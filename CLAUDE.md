# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Twitch chat bot powered by Gemini 2.5 Flash. Commands (`!who`, `!ask`, …) work as plain chat text. Free text is answered only when it contains a `сосур*` / `secur*` word (сосурян, сосурити, securityexpert, etc.), an `@botname` mention, or is a reply to a bot message. Stores full chat history in SQLite with FTS5 search and long-term memory.

## Architecture

Entry point is thin; all logic lives in `src/`, split into packages by purpose.

### Where code goes

| Package | Holds | Put here |
|---|---|---|
| `src/core/` | skeleton: config, texts, DB, logging, utils, command registry, chat dispatcher | nothing feature-specific. Features depend on core, never the reverse – the one exception is `component.py`, which registers every feature's commands |
| `src/gemini/` | everything that costs a Gemini call (incl. `picture/` – `!ascii`) | a command that generates text (`kind=Kind.GEMINI`), anything that builds prompts |
| `src/local/` | сосурян's own features without Gemini: simple commands, follow replies, emote spam, the periodic command reminder, and the `roll/` game | a small command or event reply served from SQLite + `CONTENT.md` |
| `src/local/roll/` | the «залупа стрима» game: throws, channel-points rewards, title announcements. A local feature that grew big enough for its own subpackage | anything about `!roll` |
| `src/cli/` | `bot.py --…` commands; the bot does not start | a maintenance command |

A feature that grows its own tables, texts and background loops gets **its own subpackage inside the package of its kind** – `local/<feature>/` like `local/roll/`, or `gemini/<feature>/` if it generates text – instead of spreading across several files of `local/` and `core/`: roll is a local feature of the bot, not a top-level one. Table schema and migrations still go into `init_db()` in `src/core/database.py` (one place to keep startup idempotent); the feature's queries live in its package, like `src/local/roll/storage.py`. Each package's `__init__.py` lists its modules. Paths to `CONTENT.md` and `chat_history.db` live in `src/core/paths.py`: they default to the repository root via `Path(__file__).parents[2]`, and `BOT_DB_PATH` / `BOT_CONTENT_PATH` move them – that is how the container keeps its data on a volume instead of inside the image. `database.py` and `content.py` re-export `DB_PATH` / `CONTENT_PATH` under their own names, because callers import `get_db()` rather than the path, and the tests patch them there.

### Modules

- `bot.py` – `Bot(commands.Bot)` only: lifecycle (`setup_hook`, `event_ready`, `event_oauth_authorized`), EventSub subscriptions, `send_chat_message()`, cooldown storage, background task startup, broadcaster token check (`_add_broadcaster_token()`), reward start (`_start_rewards()`) and pause on `close()`, `run_bot()`. `__main__` delegates to `src/cli/main.py`, falls back to `run_bot()`. Holds the stream state: `stream` (`StreamTracker`), `session_id` / `stream_live`, `fetch_live_stream()`, `_sync_stream()`, `stream_went_online()` / `stream_went_offline()` (shared by the events, startup and the watch loop), `_stream_end_from_vod()`, `event_stream_online` / `event_stream_offline`; `_start_memory()` and `_memory_task` (the memory loop, see Background tasks)

**core**
- `src/core/component.py` – `ChatComponent`: command registry wiring, `event_message` dispatcher (`_route()` + cooldown + role check), `event_follow` (delegates to `src/local/follow.py`). Command trigger constants live here; `SOSUR_VARIANTS` / `SOSUR_RE` live in `src/core/utils.py`, not here: `database.py` needs the same pattern for the one-off backfill of `chat_messages.addressed`, and importing the dispatcher there would be circular
- `src/core/commands.py` – `CommandContext` (dataclass: message, user, prompt, original_text, session_id, bot, kind, args; `.original_args` – the args in their original case; `.clear_cooldown()` releases its own scope), `CommandEntry`, `CommandRegistry`. Entry carries `prefix`, `role` (`Role`) and `kind` (`Kind.LOCAL` / `Kind.GEMINI`); both are `StrEnum`s, so their values are the same strings the cooldown keys and the database hold. Roles are checked by `_has_role()` in the dispatcher against the **badges**, not the collapsed tier from `tier_of()` – that one folds subscriber and VIP together for the cooldown, and a subscribing VIP would otherwise be refused where VIPs are let in
- `src/core/config.py` – env only (secrets, numbers, flags): parsing with validation (`_env_int`, `_env_float`, `_env_bool`, `_env_percent`) and config classes `Logging`, `Twitch`, `Gemini`, `Chat`, `Caps`, `Cooldown`, `Stream`, `Roll`, `Rewards`, `Context`, `Summary`, `Who`, `Proactive`, `Emote`
- `src/core/paths.py` – `DB_PATH` and `CONTENT_PATH`: the repository root by default, moved by `BOT_DB_PATH` / `BOT_CONTENT_PATH`. Imports `config` first, so `.env` is applied before the paths are computed
- `src/core/content.py` – everything the bot says, from `CONTENT.md`: `Content.prompt()`, `.label()`, `.text()`, `.items()`, mtime-cached `_ContentFile`, `validate_content()` (startup check against `REQUIRED`)
- `src/core/database.py` – SQLite async (aiosqlite): `count_bot_uses_since()` counts a journal per stream, not per sliding window; shared connection via `get_db()`/`close_db()`, schema and migrations for **all** tables (roll ones included), chat / facts / knowledge queries (`has_chatted()`, `get_chat_after()` for the command reminder, `get_last_tagged_interaction()` for `!ask` follow-ups), FTS5 search, `backup_db()`, `vacuum_db()`; `streams` queries (`get_stream`, `get_last_stream`, `save_stream`, `end_stream`, `reopen_stream`, `last_chat_time`, `get_session_start`, `get_previous_stream_session`)
- `src/core/activity.py` – `ChatWatch`: remembers the last chat message a loop has seen; `new_messages(session_id)` is true only if someone wrote since. Used by the reminder, proactive remarks and emote spam, so the bot talks only into a live conversation
- `src/core/viewer.py` – the viewer status ladder: `Tier` (`StrEnum`), `tier_of(chatter)` and `by_tier(tier, sub=, vip=, regular=, broadcaster=)`, a moderator getting the subscriber's value. Roles are not here: `_has_role()` reads the badges themselves
- `src/core/followers.py` – `FollowerCache`: фолловер ли зритель, по Helix с TTL-кэшем, ошибка трактуется в пользу зрителя
- `src/core/stream.py` – `StreamTracker`: the session is the stream. `online(stream_id, started_at)` reuses the session of a known stream id (bot restart) or of the previous stream if the new one starts within `STREAM_RESUME_MINUTES` (outage); `offline()` closes it; `settle_missed_end()` closes a stream whose end the bot never saw. Offline the session is the date. A known id that was closed is reopened (`reopen_stream()`). An end the bot never saw comes from the stream's VOD (`Bot._stream_end_from_vod()`: archive whose `created_at` is within 5 min of the start, plus `duration`), else from the last chat message the bot recorded. `watch_stream(bot)` polls Twitch every `CHECK_SECONDS` (120) and applies a disagreement only after `CONFIRMATIONS` (3) consecutive matching checks – catches lost events and changes that happened while the bot was down, without flapping on Helix lag
- `src/core/logging_setup.py` – `setup_logging(default_level)`: console handler always, rotating file handler when `LOG_FILE` is set
- `src/core/utils.py` – what every package uses: `SOSUR_VARIANTS` / `SOSUR_RE`, `clean_nick` (`NICK_MAX`), `safe_format`, `defuse`, `reply_to_bot` (the bot's line a message replies to: twitchio's `ChatMessageReply` carries `parent_user`, not `parent_user_id` – a `parent_user_id` lookup never matches, and replies then work only because Twitch prefixes them with `@botname`), `random_delay`, `local_time` (a moment in `BOT_TIMEZONE`), `gather_cancelling`

**gemini**
- `src/gemini/client.py` – Gemini client (`get_client()`), `generate()` with retries (`contents` is a string or a list of parts – that is how `!ascii` sends the image), `make_gen_config()`, `SAFETY_OFF`
- `src/gemini/context.py` – `ContextBuilder`: assembles Gemini prompts from named sections. `build()` renders full prompt; `build_without(*labels)` renders fallback
- `src/gemini/output.py` – what a Gemini answer goes through before chat: the Twitch limit `TWITCH_MSG_MAX` (450), `CHUNK_SEND_DELAY`, `WHO_MAX`, `is_caps`, `caps_preserve_mentions`, `strip_markdown`, `split_into_chunks`, `fix_dashes`, `strip_links`, `strip_pings`, `trim_to_sentence` (a sentence ends on `.!?…` **before a space or the end**, so the dot of «23.06» cut in half is not one), `cleanup_response`, `find_banned`. `cleanup_response()` (every `respond_and_save()` answer) cuts an over-long answer at a sentence end via `trim_to_sentence()` instead of mid-word with `...`, removes the asker's nick only at the very start (the reply adds it anyway) – further mentions keep the nick without `@`, because on `!who` about oneself or `!versus` with oneself deleting them left «Победитель – .»; the match has a word boundary, so `@gop` does not eat into `@gop5ter`. It also drops `*` and turns line breaks into spaces. `strip_markdown()` keeps `_` – it is part of nicks (`m1ndsh1ft_`), and removing it makes `!summary` mention people who do not exist. The dash left where the leading nick was removed goes too, and `fix_dashes()` turns the model's em dashes into `–` there and in `send_chunked()`. The separator after a removed leading nick goes with it (`@ник: …`, `@ник – …`), but only a free-standing dash – `-5` stays. `send_chunked()` trims at a sentence end to `limit × (450 − CHUNK_SLACK)` **before** splitting: a text of exactly `limit × 450` otherwise splits into `limit + 1` word-broken chunks and `[:limit]` silently drops the tail
- `src/gemini/responder.py` – shared response pipeline: `respond_and_save()` (optionally over several messages via `max_chunks`; cleanup → moderation → CAPS → emote → respond as `@ник ответ`, no colon or dash after the nick → save), `send_chunked()`, `maybe_add_emote()`, `apply_caps()`, `passes_moderation()`
- `src/gemini/commands.py` – handlers calling Gemini: `handle_default` (context from `answer_context.py`), `handle_ask`, `handle_summary`, `handle_who` and `handle_versus` (context from `who.py`, and `handle_summary` each under its `PerStreamLimit` in `LIMITS` – the per-stream limit (`_limit_for()`), one at a time (`busy`), count only what reached chat)
- `src/gemini/limits.py` – `PerStreamLimit`: the per-stream limit of `!who`, `!versus`, `!summary` and `!ascii` – one call per viewer at a time (`busy`, taken before the first `await`), the check against `bot_uses` since the stream start, the refusal `texts.<kind>_no_left`, and a count only for what reached chat; an error after sending is logged, not answered
- `src/gemini/summary.py` – `!summary`: `mode()` (current or previous stream), `now()` / `previous()` with the chat ladder `_chat()`, `KIND` for the per-stream limit (its `PerStreamLimit` lives in `commands.LIMITS`)
- `src/gemini/who.py` – the context of `!who` and `!versus`: `material()` draws a fresh random sample of a chatter's whole history on every call – memory events, content messages spread over their streams, two relations, the last messages (`Material`, with `add_sample()` / `add_old()`); `who_rungs()` and `versus_rungs()` (half the sample per person via `versus_material()`) build the ladders with the bot's previous answers about the target or pair as «do not repeat»; `WHO_KIND` / `VERSUS_KIND` for the per-stream limit, `who_tag()` / `versus_tag()`, `interaction_lines()`
- `src/gemini/ladder.py` – the fallback ladder shared by free-text answers, `!who`, `!versus` and `!summary`: `Rung` (name, prompt), `walk()` goes down while Gemini's input filter blocks, `unique_rungs()` drops rungs that came out identical
- `src/gemini/answer_context.py` – the free-text answer's context: `Question`, `ladder()` (rungs from two streams plus memory down to the narrow fallback), `answer()` walks it with `ladder.walk()`. Shared with `--probe-context`, so the probe measures what the bot sends
- `src/gemini/proactive.py` – `proactive_loop()`
- `src/gemini/memory/` – long-term memory of chatters. `storage.py` – queries on `chronicles` (row status `ChronicleStatus`), `chatter_events`, `chatter_profiles`; `Block` is one conversation and `chat_blocks()` splits chat into them by silence, `build.py` – `write_chronicle()`, `update_profile()`, `first_profile()` (backfill), `process_block()`, `catch_up()`, `memory_loop()`. Read by free-text answers (`answer_context.py`: profiles, the previous chronicle); `!who` and `!versus` read random events and relations from it (`who.py`); proactive remarks do not use it
- `src/gemini/picture/` – `!ascii`: картинка по ссылке в брайль-арт. `fetch.py` – скачивание со всеми проверками, `render.py` – пиксели в символы Брайля плюс `preview()` для Gemini, `command.py` – хендлер, кэш по ссылке и поиск ссылки в чате

**local/roll** – the «залупа стрима» game

No chat, no Twitch. Also the perks: `grant_perks()`, `appear()`, and inside throws `_take_perk_curse()` / `_perk_shield_left()`

- `src/local/roll/perks.py` – chat side of the perks: `on_stream_start()` grants and announces, `on_chat()` starts a player's countdown on their first message (pending names cached per session)

**cli**
- `src/cli/main.py` – argparse and the command bodies; a command that needs the database is wrapped in `_with_db` (`init_db()` before, `close_db()` after, whatever happens), and logging is set up once for all of them; `_check_combination()` allows one command per run and accepts a modifier (`--dry-run`, `--source`, `--limit`, …) only with a command that reads it – `--vacuum --dry-run` would otherwise compact the file for real – and never without one, since with no command `bot.py` starts the bot and a stray flag would bring up a second instance (`--upload-lore` with `--format` / `--source`, `--lore-sources`, `--list-facts`, `--build-memory`, `--clear-memory`, `--probe-context`, `--backup`, `--vacuum`, `--sync-emotes`, …)
- `src/cli/memory.py` – `--build-memory`: on an empty memory chronicles of every finished conversation in parallel, on an existing one failed chronicles again and new conversations one by one as the bot does; then a first profile for every active chatter without one, then facts without an `@nick` copied into `knowledge`; prints tokens and a cost estimate from `client.usage` via `client.cost_estimate()`, the one place the prices live. `--dry-run --limit N` prints instead of writing
- `src/cli/probe.py` – `--probe-context`: asks real past addressings of the bot (chat strictly before the question; commands are skipped – a `!` at the start or after a space – while a question with `!` inside is kept) in two variants – `now` (the plain chat-window context and its fallback) and `new` (`answer_context.answer()`, the very code the bot runs, with the ladder rung that answered). Old history has date sessions only, so the probe treats them as streams (`Question.stream=True`). Writes nothing
- `src/cli/knowledge.py` – knowledge base operations: `parse_lore_file(path, fmt)` for three formats (`lines` – one entry per line; `telegram` – a Telegram Desktop export, «author: text» per message; `text` – txt/md cut into 1–3 sentence pieces), `import_entries(entries, source)` (in transactions of `IMPORT_BATCH`, 2000 rows: one transaction for a whole import held the write lock past SQLite's 5 s wait and lost the running bot's chat inserts), `clear_knowledge(source=None)`, `lore_sources()`
- `src/cli/emotes.py` – emote sync: Twitch Helix sources in `SOURCES` (`channel`, `global`), non-destructive `merge()` into the `### emotes` block of `CONTENT.md`

### `CONTENT.md` – everything the bot says

One Markdown file, four sections, read through `src/core/content.py`. Layout is `## section` → `### key` → the value, which runs until the next heading. Re-read automatically when mtime changes – edit without restarting the bot.

| Section | Accessor | Holds |
|---|---|---|
| `## prompts` | `Content.prompt(name, **values)` | `system` (personality), `ask`, `ask_followup`, `summary`, `summary_request`, `summary_request_previous`, `summary_previous`, `summary_tail`, `who`, `versus`, `proactive_user`, `proactive_general`, `user_question`, `interaction_line`, `memory_chronicle`, `memory_chronicle_merge`, `memory_profile`, `memory_hint` (free-text answers with memory) |
| `## labels` | `Content.label(name, **values)` | context section headings the model sees – `facts`, `chat`, `channel`, `language`, `user_facts`, `user_messages`, `user_interactions`, `user_events` / `user_sample` / `user_relations` / `user_recent` / `who_said` (`!who`, `!versus`), and `prev_stream` / `people` / `chronicle` / `replied` (free-text answers, `answer_context.py`). `prompts.system` refers to them by name, so they must stay in sync |
| `## texts` | `Content.text(name, **values)` | every reply sent to chat – help, stats, roll texts, reward titles/prompts/outcomes/refunds, cooldown, role refusal, usage hints, error messages |
| `## lists` | `Content.items(name)` | `emotes`, `follow`, `banned` – one entry per line, `#` starts a comment. `emotes` is also maintained by `--sync-emotes` |

Rules that make this work:
- **`.env` holds secrets, numbers and flags; `CONTENT.md` holds text.** Nothing the chat sees is hardcoded in handlers
- Placeholders (`{user}`, `{target}`, …) are substituted with `safe_format()` – a broken template logs a warning and passes through instead of crashing the handler
- Markdown has no syntax to break, so the loader checks meaning instead: a duplicate `###` key logs an error (last one wins), and a file that parses to no sections at all, or lacks any `REQUIRED` key once a complete version is loaded (caught mid-write by an editor that saves in place, or a required key renamed), keeps the previous valid version
- `<!-- … -->` lines and any prose between `##` and the first `###` are notes – they never reach the bot
- `validate_content()` runs at startup against `REQUIRED` in `src/core/content.py`: a missing key aborts the boot, an unknown heading logs a warning (that is how a typo in `###` surfaces). Add a key there when adding a text

Flow:
1. `setup_hook` – `init_db()` (opens shared DB connection, migrations, legacy cleanup), loads bot token from env, fetches broadcaster ID, adds and validates the broadcaster token (`_add_broadcaster_token()`: token owner must be the channel and carry `channel:manage:redemptions`), registers `ChatComponent` and `RewardComponent`, then syncs the stream: `_sync_stream()` asks Twitch whether the channel is live (`fetch_streams(type="live")`) – events from before the start will never arrive
2. `event_ready` – fetches bot username, calls `_subscribe_to_chat()` (chat + follow events); on failure logs a warning + OAuth URL. Starts background tasks via `_start_background_tasks()` (reconnect guard prevents duplicate tasks), then `_start_rewards()` (no broadcaster token → logs the OAuth URL for the channel account and stays off) Rewards start open only while the stream is live. When live, `perks.on_stream_start()` grants perks for the previous session – idempotent, so reconnects and restarts never duplicate the announcement. Also subscribes to `stream.online` / `stream.offline`. `_start_memory()` starts `memory.memory_loop()` once
3. `event_oauth_authorized` – saves token; prints `TWITCH_BOT_TOKEN` / `TWITCH_BOT_REFRESH` for the bot account, or `TWITCH_BROADCASTER_TOKEN` / `TWITCH_BROADCASTER_REFRESH` for the channel account and starts rewards right away
4. `ChatComponent.event_message`:
   - Computes `session_id` once as local variable (the session switches when a stream starts or ends, and coroutines outlive that)
   - Saves every non-bot message to `chat_messages` (FTS synced via trigger) **except commands to the bot**: a message that resolved to a registry entry (`!roll`, `сосурян !who ник`, …) is not stored – only live dialogue is. Commands say nothing about a person and eat the `!who` window: 30 of one chatter's last 50 messages were commands. Old command rows stay in the DB; `get_user_messages()` filters `!…` out for them
   - `perks.on_chat()` – a player's first message in the stream starts their perk countdown and announces it
   - `_route()` returns `(entry, prompt, addressed)` and runs **before** the message is saved, because `addressed` is stored with it: **every command matches the raw text first**, no addressing needed, and its args are taken verbatim (so `!who securityexpert` keeps the nick). Free text requires `(?:сосур|secur)\w*` (variants listed in `SOSUR_VARIANTS`) / `@botname` (the whole nick: `@botname_fan` is someone else) / reply to the bot, after which the trigger is stripped – the mention, or when there is none the first call word only, so a nick like `securityexpert` in the question itself reaches the model – and the command lookup runs again (`сосурян !who ник` still works)
   - Resolves the wait from the chatter's status alone (one ladder for everything), then checks it in the scope of the command's class

- **Every command works as bare text** (`!who ник`, `!ask …`), including Gemini commands: no mention is required. Only the cooldown stands between chat and Gemini spend. Free text still needs addressing.
- `!roll` – 1–100, lowest roll of the session is the "залупа стрима". Free throws depend on status: subscriber or moderator `ROLL_FREE_SUB` (10), VIP `ROLL_FREE_VIP` (5), everyone else `ROLL_FREE_PER_SESSION` (3), broadcaster unlimited; `free_limit_for(chatter)` in `src/local/roll/command.py`. The limit is stored in `rolls.free_limit` on every throw from chat, because a channel-points redemption carries no badges and `_extra()` has to know it. A new throw overwrites the previous value (UPSERT). **`ROLL_FREE_PER_SESSION` (3) free throws per session**, counted in `rolls.free_throws`; beyond that – the `extra` channel-points reward. **The broadcaster rolls without limit** (`free_throw(..., unlimited=True)` from `chatter.broadcaster`): no refusal and no `roll_free_left` note, but the throws are still counted so `extra` behaves for them like for anyone. `texts.roll_free_left` is appended as a separate key rather than a placeholder in `roll_loser_*` – see "When changing things". `texts.roll_champion` ("Достойнейший китежанин стрима", the session maximum via `get_session_champion()`, same tie-break as the loser) is appended the same way to `!roll` and to reward outcomes that change a roll; hidden when the champion is also the loser (one player, or everyone rolled the same) **Closed while the stream is offline** (`texts.roll_offline`, cooldown released) – the game lives inside a stream
- `!ascii <ссылка>` – draws a picture from a URL in **braille** (U+2800–U+28FF), **one chat message**. Twitch chat is a proportional font and collapses runs of spaces, so plain ASCII art falls apart; braille cells render at one width, U+2800 is not a space, and one cell carries a 2×4 dot matrix. A braille line holds no spaces, so it is one unbreakable word – spaces sit only between lines, wrapping happens strictly there, and every line lands on its own visual line without newlines (a Twitch message has none). The sender's nick shifts nothing: the first line does not fit beside it and moves down. Hence the budget is **characters, not lines**: a line of N costs N+1, so `_best_box()` picks the frame from the picture's proportions – a tall one gets fewer columns and more rows. `PICTURE_MAX_COLS` (26) caps the width: a wider line breaks on wrap and the picture falls apart. Binarisation is a global threshold first, and **falls back to a local one** when the result comes out flooded (ink share above `INK_MAX`, 0.45) or nearly empty (below `INK_MIN`, 0.05): a single number cannot separate a large area lying just below it, which turns a green Pepe into one black silhouette with no face. The local threshold compares a dot to its own neighbourhood (`GaussianBlur` minus the image) and keeps outlines and features inside flat areas. Dithering is not used at all – at 60 dots across Floyd-Steinberg is noise, not halftone. A picture with an **alpha channel** also gets its silhouette outlined (`_add_shape()`): a cutout on transparency carries no form of its own – a gold trophy composited on white is nearly white, the threshold loses it and only a tangle of strokes is left, and Tux's white belly disappears entirely – while the alpha knows the shape exactly. The crop box comes from the alpha too, so it is exact. An image whose alpha turns out fully opaque is treated as having none. After the threshold the ink is **hollowed out** (`PICTURE_HOLLOW`): the drawing minus itself eroded by one dot, so only edges survive. A solid blob loses its shape – a raccoon photo comes out as a black smudge with a contour around it – while thin lines are untouched, being all edge already, so drawn line art like Pepe does not change. On top of the contour the darkest places (below `PICTURE_SHADOW`, 45) stay filled: that is what gives volume instead of a wire diagram. `PICTURE_ASPECT` (0.8) squeezes the picture vertically before it is sliced into dots: the chat cell is taller than twice its width, so a braille dot is not square and an uncorrected picture looks stretched. Gemini does **not** draw: it looks at the image and either forbids it or describes it (`prompts.picture`). Only an answer starting with `МОЖНО` lets the picture through (`_allowed()`; wrapping like `**МОЖНО**` or `«Можно»` is stripped first); `НЕЛЬЗЯ`, «извини, но нельзя» or anything unparsed is a refusal (`texts.ascii_blocked`) – checking for the refusal word instead lets a reworded refusal through. **One picture per viewer at a time** (`LIMIT.busy` in `command.py`): the limit is checked first and counted after sending, seconds later, and a subscriber has neither cooldown nor quota, so without it five quick `!ascii` pass the check with the same count; repeats are dropped silently with `ctx.refuse()`. A verdict that starts with neither `МОЖНО` nor `НЕЛЬЗЯ` is refused but **not cached**, so the next try can succeed. The description never reaches chat – the picture speaks for itself and a remark on top only clogs it. `PICTURE_CHECK` (on) is the whole point of the call: the veto, and the refusal is **closed** – no verdict (timeout, network error, or Gemini refusing to answer about that image) means the picture is not drawn (`texts.ascii_unchecked`), and that failure is not cached, so a retry can still succeed. `_look()` is also **the one place in the project where Gemini safety filters are on** – `SAFETY_CHECK` in `client.py`: sexual and dangerous content at `BLOCK_MEDIUM_AND_ABOVE`, harassment and hate off, because memes are made of them. Everywhere else the filters are off on purpose because the persona needs it, but here the task is the opposite – Google's own classifier becomes a second layer beside the prompt, since an image it will not discuss yields no text, which is already a refusal. The config goes through `make_gen_config(persona=False, temperature=CHECK_TEMPERATURE, safety=SAFETY_CHECK)`, like every other request: a hand-built config drops `thinking_config`, and the check then thinks dynamically at output prices. It runs without the persona and at `CHECK_TEMPERATURE` (0.2): a verdict should not drift. **Open from the subscriber badge up** (`Role.SUB_VIP_MOD_BROADCASTER`): a follower and a non-follower cannot use it at all. Per stream a VIP draws `PICTURE_PER_STREAM_VIP` (3), a subscriber or moderator `PICTURE_PER_STREAM_SUB` (10), the broadcaster is unlimited (`_limit_for()`). Counted in `bot_uses` under kind `ascii` since the stream start (`count_bot_uses_this_stream()`, shared with `!who`), so a restart does not reset it; offline, where the session is a date, the window is 24 hours. Only a picture actually shown counts – every refusal is free – while a cache hit does count, because the viewer still filled the chat with a picture. **The link must be in the command itself**: without one the bot answers `texts.ascii_usage` (quota refunded). The last link in chat is not taken: it guesses the wrong picture, and command messages are not stored anyway. Results are **cached by URL** (`CACHE_SIZE`, 32, in memory, until restart): chat repeats the same meme all evening, and a repeat costs no download, no render and no Gemini call – the verdict is cached too, so a link already approved stays approved for the session. A repeat still spends the hourly quota: the quota limits how often a viewer makes the bot act, not what it costs us. Gemini gets a **downscaled copy** (`preview()`, 512 px, JPEG): the model only has to say what is on the picture and whether it may be shown, and resolution does not change that – on a photo this cuts the payload by about 90%. The description is **saved to `bot_interactions`** under `[ascii] <url>`, so the bot knows what it showed and can talk about it later, but it is never said in chat at the time. `PICTURE_ENABLED=false` **unregisters** the command instead of leaving it silently inert. The SSRF guard checks names *and* the address the connection actually reached (`_check_peer()` via `response.extensions['network_stream']`), because httpx resolves the name a second time and a zero-TTL record would otherwise swap it between check and request; an unknown peer address is a refusal, not a pass. The client ignores the environment's proxy settings (`trust_env=False`: behind a proxy the peer check would see the proxy) and asks for an uncompressed body (a compressed one is decoded past `MAX_BYTES` chunk by chunk), and the whole download, redirects included, has a deadline of `PICTURE_TIMEOUT × 2`: httpx's own timeout is per operation, so a server dripping a byte at a time would hold the viewer's slot indefinitely. `MAX_PIXELS` is tested between `Image.open()` and `img.load()` – the header carries the size, and a 100 KB png expanding to 150M pixels must be refused before it is decoded, not after. Both the art and the preview go through `render._open()`, which decodes a JPEG at a reduced scale right away (`draft`) and shrinks any picture to `WORK_PX` (1024) before colour conversion, compositing and crop: the art is at most 52 dots wide, and working on the full size took ~580 MB for a 36-megapixel picture with transparency (now ~300 MB, a JPEG ~20 MB). The URL is taken from `ctx.original_text`, not `ctx.args` – the latter is lowercased and a URL path is case-sensitive. `ctx.refuse()` refunds the quota only for a missing or rejected URL: a download that happened cost traffic, and refunding it would make downloading free and unlimited
- `!help-bot` – **lists the command names only**, with no descriptions and no role marks. What each one does lives in the channel description under the stream: descriptions do not fit into one 450-character Twitch message. The trigger carries the `-bot` suffix so it does not collide with other bots' `!help`. `texts.help` receives `{min}` / `{max}` from the handler, so roll bounds can be put into the text without touching code
- `!rollstat` – how the game stands, without throwing: the caller's own roll and free throws left, their curse (ceiling of the next throw, and the minutes left once it sits on the floor) or shield, then the session's залупа and китежанин. `game.status()` **only reads** – it goes through `get_roll()`, `rules.curse_of()`, `get_perk()` and `_standings()`, and deliberately not through `_perk_shield_left()`, which activates the perk: asking about your standing must not start the countdown. Texts are `texts.rollstat_*` plus the shared `roll_free_left` and `roll_champion`; offline it answers `texts.roll_offline` and releases the cooldown, like `!roll`
- `!stat` – three keys joined with a space, **the caller's own numbers first**: `texts.stats_self` (or `_day` when offline), then the stream line `texts.stats_stream` (`_day` offline, `Стрим от 17.09.2026` – the day only, no time), then `texts.stats_total` for the channel, joined with ` | ` so the three blocks do not run together. **The order inside the answer:** own messages this stream → own requests to the bot this stream → own messages and requests all time → the stream's messages and requests → the channel's all-time messages and requests. Channel-wide numbers carry «всего» so they cannot be read as personal ones. `!stat <ник>` answers about another viewer with `texts.stats_user` / `_day`, or `texts.stats_unknown` for a nick never seen in chat. **«Обращений» counts the addressings themselves, not the answers**: the number comes from `chat_messages.addressed`, set by the dispatcher for a сосур*/secur* call, an `@botname` mention or a reply. So an addressing counts even when the bot stayed silent (empty Gemini answer, stop-list, cooldown) A call that carries a command (`сосурити !roll`) does not count: command messages are not stored at all, so only free-text addressings count. Counting `bot_interactions` instead undercounts badly: 3 requests against 7 real addressings in one stream, because that table holds answers plus everything the bot says on its own. `get_total_stats()` still counts streams and offline days separately (session id longer than 10 chars = stream), but the text does not show them; `{streams}` / `{days}` are still passed, so they can be put back by editing `CONTENT.md` alone. `get_user_stats()` returns four numbers, and all four are shown: session messages, session requests, all-time messages, all-time requests
- `!summary` (`src/gemini/summary.py`) – **the whole current stream** (up to `CONTEXT_STREAM_MAX_MESSAGES`; a 500-message window loses the start of 800+ message streams), down a ladder via `ladder.walk()` when Gemini's input filter blocks it: whole stream → last `CONTEXT_SUMMARY_MESSAGES` → last 200. `!summary прошлый` (any arg starting «прош»; the trigger is a prefix entry now) and any `!summary` offline retell **the previous stream**: the latest other session with `MEMORY_CONVERSATION_MIN_MESSAGES`+ messages (`get_last_chat_session()`), from its chronicle (`storage.session_chronicle()`, `prompts.summary_previous`) or, while the memory has not written it yet (it waits `MEMORY_SILENCE_MINUTES`), from its chat (`prompts.summary_request_previous`). **Limited per viewer and stream** like `!who` / `!versus`: follower `SUMMARY_PER_STREAM_FOLLOWER` (1), VIP `SUMMARY_PER_STREAM_VIP` (3), subscriber / moderator `SUMMARY_PER_STREAM_SUB` (10), broadcaster unlimited; the current and the previous stream share one count (`bot_uses` kind `summary`, `texts.summary_no_left`). `send_chunked()` returns whether anything went out, and only that is counted. `prompts.summary` asks for the topics plus 1–2 most shameful moments with a quote, at most 650 characters, and `prompts.summary_tail` repeats the length and no-lists rule **after** the chat: stated only before it, 2 of 4 summaries run to 1000–1250 characters (one as a list) and the 850 cut drops the shameful moments at the end. `prompts.system` + `prompts.summary` overlay, temperature 1.2, **at most `CHAT_MAX_CHUNKS` (2) messages**, cut at a sentence end. `get_recent_chat()` skips old `!…` rows, so commands never reach the summary, the free-text context or proactive remarks
- `!who <ник>` / `!versus` – the nick is cleaned by `clean_nick()` in `src/core/utils.py` (no `@`, no trailing `,.:;!?`, lowercase), shared with `!stat`. **`!who` per-stream limit**: follower `WHO_PER_STREAM_FOLLOWER` (1), VIP `WHO_PER_STREAM_VIP` (3), subscriber / moderator `WHO_PER_STREAM_SUB` (10), broadcaster unlimited – the same numbers as `!summary` (`_limit_for()` in `commands.py`, a subscribing VIP counts as a subscriber). Counted like `!ascii`: `bot_uses` kind `who` since the stream start via `count_bot_uses_this_stream()` (shared with `!ascii`; offline a 24-hour window), and only for an answer that reached chat. Exhausted – `texts.who_no_left` and `ctx.refuse()`. One `!who` per viewer at a time (`PerStreamLimit.busy`, taken before the first `await` – taking it after the count lets two concurrent commands through with the same count). **`!who` is not a dossier**: a handful of facts in random order plus a joke or two, with as much of the history covered as possible. `src/gemini/who.py` samples afresh on every call – `CONTEXT_WHO_EVENTS` (15) random memory events, `CONTEXT_WHO_SAMPLE_MESSAGES` (40) random messages of 25+ chars taken round-robin over the target's sessions (one busy stream cannot fill the sample), `CONTEXT_WHO_RELATIONS` (2) relations from the profile, the last `CONTEXT_WHO_RECENT_MESSAGES` (10), and the bot's last two `[who] ник` answers (`get_tagged_answers()`) as «already said». The profile's portrait is left out on purpose: the model retells it the same way every time. A 30-message window covers 1% of an active chatter, so three calls describe the same latest topic. Ladder via `ladder.walk()`: whole sample → 40% of it → the fallback context (last `CONTEXT_WHO_MESSAGES`, facts, interactions). Messages exclude commands. A nick with no data gets `texts.who_unknown` **and `ctx.refuse()`** – Gemini was not called, so a typo costs no cooldown or quota. `!versus` refuses the same way when **either** nick has no data (`texts.versus_unknown` for both, `texts.versus_unknown_one` for one) – with one side empty the model invents that person. **`!versus` is a battle, not two dossiers**: the bot piles up two facts about each from the same random sample as `!who` (half the size per person), mocks them, names the loser – whoever's facts are dumber and more out of place, no draws – and ends with a roast of both; the pair's previous answers in either order go in as «already said». Same per-stream limit numbers as `!who`, its own count (`bot_uses` kind `versus`, `texts.versus_no_left`). `prompts.versus` asks for at most 650 characters: at 750, two answers of six run past the two-message budget (850) and lose the final roast. `!versus` answers in **up to two messages** (`respond_and_save(..., max_chunks=VERSUS_MAX_CHUNKS)`): two descriptions plus the verdict do not fit one, and trimming cuts exactly the verdict; `prompts.versus` demands a winner, no draws
- `!ask` – factual mode: `prompts.ask` as system instruction, no personality and no channel context, but the model is told it answers a viewer in Twitch chat and must not invent anything about the game or bot commands. Own temperature `GEMINI_ASK_TEMPERATURE` (0.5): at the chat temperature (1.7 in `.env`) it invents facts. The question goes to the model **in its original case** (`ctx.original_args`). The viewer's previous `!ask` within `ASK_FOLLOWUP_MINUTES` (15) is sent along via `prompts.ask_followup` (`get_last_tagged_interaction()`), so a follow-up like «а подробнее?» works. **At most two Twitch messages**: `send_chunked(..., max_chunks=ASK_MAX_CHUNKS)`, which cuts the answer at a sentence end to fit. `GEMINI_THINKING_BUDGET` is not applied to `!ask`

## Channel-points rewards

Four rewards, created and managed by the bot itself. Twitch lets only the app that created a reward fulfill or refund its redemptions – a reward made by hand in the dashboard is useless to the bot.

| Action | Input | Effect | Refunded when |
|---|---|---|---|
| `extra` | – | a throw for yourself beyond the free ones; does not touch `free_throws` | free throws are still left |
| `reroll` | nick | throws for the target, new value replaces theirs. A target who has not rolled this session gets its first roll this way (`texts.reward_reroll_first`), but only for a nick the bot has seen (`has_chatted()`: a chat message, a roll or a Gemini request – commands are not stored in `chat_messages`), so a typo cannot create a phantom player. On a cursed target the throw is capped by its ceiling and lowers it one step, like the target's own throw. **A successful reroll makes the target immune to further rerolls for `REWARD_REROLL_PROTECT_MINUTES` (3)** – Twitch's per-user limit counts each attacker separately, so several viewers can pile on one target (5 rerolls on one player in 3 minutes). Refused rerolls do not extend the window; `curse` pierces it like the shield. Counted by SQLite from the last `ok` reroll in `roll_actions` | bad nick, self, no roll and never seen in chat (`unknown_target`), target shielded, target was rerolled less than `REWARD_REROLL_PROTECT_MINUTES` (3) ago |
| `curse` | nick | **pierces the shield.** Throw capped at `REWARD_CURSE_CEILING` (75); every later throw on the target – its own `!roll` / `extra` **or someone's `reroll`** – lowers the ceiling by `REWARD_CURSE_STEP` (5) down to `REWARD_CURSE_FLOOR` (25). The ceiling holds on the floor for `REWARD_CURSE_HOLD_MINUTES` (15), then the curse lifts. A new session lifts it too | bad nick, self, target has not rolled, target already cursed |
| `shield` | – | protects from `reroll` until the session ends; not from `curse` | already shielded |

- **Curse state lives in `rolls`:** `curse_ceiling` (ceiling of the next throw, NULL = not cursed) and `curse_floor_at` (`time.time()` when the ceiling reached the floor). Expiry is lazy for the game – `rules.curse_of()` in `src/local/roll/rules.py` stops treating the row as cursed once the hold has passed. The row itself is cleared by `game.lift_expired_curses()` from `curse_lift_loop`, which announces the lift in chat exactly once
- **With 3 free throws most victims never reach the floor on their own:** 75 → 25 takes 10 throws, so without paid `extra` or other viewers' rerolls the curse lasts the whole session at a ceiling of 60 or above. Rerolls cut both ways: each one hurts the victim and brings the floor – and the 15-minute countdown to lifting – closer

- **Fully automatic.** Every redemption is applied and immediately set to FULFILLED or CANCELED (points back). Nobody confirms anything
- **Broadcaster token required.** The bot's moderator rights are not enough. `_add_broadcaster_token()` takes the channel's token from twitchio's store first (loaded from `.tio.tokens.json`, saved there on graceful shutdown and fresher after refreshes), then from `TWITCH_BROADCASTER_TOKEN` / `_REFRESH`. So an OAuth login survives a normal restart even if the console values were never copied – but not a `kill -9`. Without it rewards stay off and the OAuth URL for the channel account is logged; `REWARDS_ENABLED=false` silences that
- **Sync on start, not hot.** Table `rewards` maps action → Twitch reward id. Titles and prompts come from `CONTENT.md`, costs and per-user limits from `.env`; `_changes()` patches only fields that differ. A lost `rewards` table is recovered by matching titles among the app's own rewards
- **Journal `roll_actions`** – one row per redemption, `redemption_id` UNIQUE. It is the duplicate guard (EventSub may redeliver) and the shield store: a shield is an `ok` row with `action='shield'`. Check and write happen under the same lock as the throw
- **Paused while the bot is down.** `Bot.close()` pauses rewards before twitchio closes its HTTP session. After a crash `_settle_stale()` refunds redemptions left UNFULFILLED from before the subscription, or fulfills them if the journal says they were applied Also paused while the stream is offline: `RewardService.set_open()` follows `stream.online` / `stream.offline` and records the wanted state even before `start()` is done, so a stream that goes live while `start()` is still creating rewards and subscribing is not lost; `start()` applies the latest state, and a failure to pause or to settle stale redemptions after the subscription is logged rather than leaving the service half-started, and a redemption that slips through offline is refunded with `texts.reward_refund_offline`
- **twitchio 3.x bug:** `CustomRewardRedemption.fulfill()` sends the channel id instead of the redemption id, so every status goes through `_http.patch_custom_reward_redemption()` directly
- **Commands are not in `chat_messages`, and some readers see less.** The stream end estimated from the last chat message (no VODs, bot was down) ignores a closing `!roll` spree; the proactive loop, emote spam and the command reminder treat a chat of only commands as silent – intended: the bot speaks only into live dialogue. `!stat <ник>` and reroll targets use `has_chatted()`, which also looks at `rolls` and `bot_uses`, so a viewer who only types commands is not «unknown»
- **Session = stream.** Free throws, shields, curses and perks belong to the stream: a stream across midnight is one game, and a bot restart or a short outage mid-stream loses nothing. **Known limit:** with VODs off, if the bot was down long before the stream ended, the end is taken from the last chat message it recorded, so a stream restarted soon after the real end may become a new session

## Perks from the previous stream

At the start of a stream (`stream.online`, or `event_ready` when the bot starts mid-stream) `game.grant_perks()` takes the **previous stream** (`get_previous_stream_session()` from `streams`; if that stream had no rolls there are no perks, older streams do not count; when no earlier stream is recorded, the latest date session whose rolls ended before this stream started – `get_last_roll_session_before()`) and gives its **champion a shield** and its **loser a curse** (table `roll_perks`, `INSERT OR IGNORE` – safe to repeat). If champion and loser are the same person only the curse is given. Announced once with `texts.roll_perks_both` / `_champion` / `_loser`.

- **Countdown starts on first appearance**, not at stream start: the player's first chat message (`perks.on_chat()` → `game.appear()`, announced with `texts.roll_perk_shield_on` / `roll_perk_curse_on`) or the first throw on them (activated silently inside the game). Lasts `ROLL_PERK_MINUTES` (30)
- **Shield perk** blocks rerolls like a bought shield, refund text `texts.reward_refund_perk_shield` with minutes left (status `perk_shielded`). Curse pierces it
- **Curse perk** is laid on the first throw on the loser inside the window (`_take_perk_curse()` in `_throw_for()`): ceiling `REWARD_CURSE_CEILING`, the usual ladder, **plus a hard deadline** `rolls.curse_until` = end of the window. It is given once (`consumed`); a loser who never shows up inside the window loses it. `curse_lift_loop` announces the lift when the deadline passes
- In short: countdown from first appearance, curse = normal curse + 30-minute cap, session = stream for the whole bot, game closed offline

## Background tasks

Each lives in its feature package – `proactive_loop` in `src/gemini/proactive.py`, `emote_spam_loop` in `src/local/emote_spam.py`, `help_loop` in `src/local/help_announce.py`, `curse_lift_loop` in `src/local/roll/announce.py` – all started in `event_ready`, task references on `Bot._proactive_task` / `Bot._emote_spam_task` / `Bot._help_task` / `Bot._curse_lift_task` / `Bot._stream_watch_task` (`watch_stream` in `src/core/stream.py`, always on, sends nothing to chat). Two more loops live in `bot.py` itself and send nothing either: `_chat_watch_task` (`_watch_chat_socket()`, every `CHAT_WATCH_SECONDS` (60) resubscribes to chat when the EventSub socket is gone) and `_heartbeat_task` (`_beat()`, touches `BOT_HEARTBEAT` for the healthcheck). With `_memory_task` that is eight, all stopped by `stop_background_tasks()`. There is no periodic «залупа стрима» announcement (`roll_status_loop`, `ROLL_ANNOUNCE_*`, `texts.roll_announce*`): every `!roll` and reward outcome already names the loser and the champion.

- `proactive_loop` – after a random pause of `PROACTIVE_INTERVAL_MIN_MINUTES`..`PROACTIVE_INTERVAL_MAX_MINUTES` (5–30), re-rolled before every iteration: a fixed cadence reads as a schedule. **Only into a live conversation**: skipped unless someone wrote since the previous remark (`ChatWatch`) – otherwise it comments a chat that has been silent for an hour. With `PROACTIVE_TARGET_PROBABILITY` chance targets a random user from the last `PROACTIVE_ACTIVE_WINDOW` messages, otherwise comments generally. Full context, CAPS, emote, moderation check. Saved under `_proactive_` username
- `emote_spam_loop` – after a random pause of `EMOTE_SPAM_INTERVAL_MIN_MINUTES`..`EMOTE_SPAM_INTERVAL_MAX_MINUTES` (5–20), sends `EMOTE_SPAM_MIN`..`EMOTE_SPAM_MAX` random emotes. **Only while live and only if someone wrote since the previous batch** (`ChatWatch`) – otherwise it posts into an offline, empty chat too. No Gemini
- `help_announce.help_loop` – every `HELP_ANNOUNCE_INTERVAL_MINUTES` (30) posts `texts.help_announce`, the command list, so a viewer who joined mid-stream learns what the bot can do. **Only while the stream is live and only when somebody has written since the previous reminder** (`ChatWatch` in `src/core/activity.py` over `get_chat_after()`) – a chat gone quiet gets nothing and two identical reminders never run back to back. Skipped as well when someone called `!help-bot` in that time: the list was just in chat. `!help-bot` is a command and so not in the DB – `handle_help` marks itself via `help_announce.note_help_shown()`. Not saved to `bot_interactions`: it is an announcement, not an interaction. No Gemini
- `curse_lift_loop` – runs while `REWARDS_ENABLED=true` or `ROLL_PERKS_ENABLED=true`, checks every `CURSE_LIFT_CHECK_SECONDS` (60, a constant in `announce.py`). `game.lift_expired_curses()` clears, under the game lock, every curse of the current session whose ceiling sat on the floor for `REWARD_CURSE_HOLD_MINUTES` or whose hard deadline `curse_until` passed; each lift is announced with `texts.roll_curse_lifted` and saved as `_roll_` / `[curse-lifted]`. Clear first, send second: a failed send loses that one message but a lift is never announced twice. A curse that never reaches the floor ends silently with the session. No Gemini

- **memory** (`src/gemini/memory/build.py`) – `memory_loop()`, started by `Bot._start_memory()` on `event_ready`: `catch_up()` right away and every `CHECK_SECONDS` (600). **It goes by silence in chat, not by the stream state**: chat here happens only on streams (2 messages off-stream vs 1301 on streams since streams are tracked), so a conversation (`storage.Block`, chat between two silences of `MEMORY_SILENCE_MINUTES`, 180) is a stream in practice, and no missed Twitch event, restart or stream that ended while the bot was down can shift it. Waiting `STREAM_RESUME_MINUTES` after `stream.offline` instead would put the memory off until the next stream on a restart inside that window, and post-stream chat would fall into a separate day session. Over the whole history there are 71 silences over 6 h and one between 3 and 6 h. What is done is decided by coverage: a chronicle row covers `first_id..last_id` of `chat_messages`, so order and parallel writes do not matter. For each finished conversation with `MEMORY_CONVERSATION_MIN_MESSAGES` (50)+ messages: a chronicle plus per-chatter events (one call, JSON schema), then a rewrite of the profile of everyone with `MEMORY_PROFILE_MIN_MESSAGES` (10)+ messages in it (skipped if already updated with exactly this conversation – a rerun after a crash), then the chronicle row. Fewer messages – a `skipped` row, no Gemini. Only when Gemini did not answer at all (`Unavailable`: timeout, network, quota, a bad key or retired model – 403, 404, `FAILED_PRECONDITION`, `API_KEY_INVALID`) is the conversation left unmarked and retried in 10 minutes. An answer with no text and no named filter (`EMPTY` from `generate_checked()`: RECITATION, OTHER, …) or a request the API rejected (`ERROR`: 400 `INVALID_ARGUMENT` or 413 – the request itself) is asked once more and then counts as a failure – it repeats for the same prompt, and treating it as an outage replays the conversation every check; anything else is final and written as `failed` – a chat the filter refuses for good would otherwise stop every later conversation behind it. `catch_up()` does nothing until `memory_state.built` is set by `--build-memory`: the history is its job, and a half-built memory (build killed or still running) would otherwise be replayed conversation by conversation at ~3.5× the calls. **The bot's own lines never go in**, as in the chat window: quoting itself makes the bot loop. Prompts ask for the chat's own voice (irony, slang, verbatim quotes) with nothing invented; temperature 0.9, no persona, no thinking. Gemini's input filter (`PROHIBITED_CONTENT`, cannot be disabled) judges a combination of messages: one chat was blocked whole and in eighths but passed in sixteenths, so a blocked chronicle is split in halves down to `CHRONICLE_MIN_PIECE` (50) and the pieces merged into one by another call (`prompts.memory_chronicle_merge`; joined as is if that fails – joined pieces ran 3–5× a normal chronicle), and a blocked profile is retried without mentions, then on the last 200 / 100 / 50 messages. `_migrate_memory()` checks the result of every step, so a migration killed halfway (SQLite commits `ALTER TABLE` at once) finishes on the next start. Gemini also has a random output filter (`finish_reason` `PROHIBITED_CONTENT`, no text): `generate_checked()` tells `BLOCK_INPUT` from `BLOCK_OUTPUT`, and an output block is simply asked again (1 profile of 80 in the backfill, the same prompt passed 3 of 4 times); `BLOCK_OUTPUT` only when there is no text at all, so chat answers still send whatever came back. Only an input block splits: a timeout or an unreachable Gemini is not split – that turns a 13-second failure into half an hour. **Memory never slows chat answers**: its requests take at most `MEMORY_CONCURRENCY` (2) of the `GEMINI_CONCURRENCY` (5) slots; `--build-memory` lifts that (`use_all_slots()`). Measured on a copy of the live DB: ~$0.005–0.01 per chronicle or profile; the whole backfill (89 chronicles, 12 of them split, 80 profiles) takes 4 minutes and ~$0.8

The three chat loops send via `Bot.send_chat_message()` (HTTP API, no reply badge), log when stopped, and never die from a single failed iteration.

## Database (chat_history.db)

A script that touches the DB must end with `close_db()`: the open aiosqlite connection keeps a non-daemon thread alive, and the process never exits. This looks like a Gemini call hanging for minutes.

Fourteen tables + two FTS5 virtual tables:
- `chat_messages` – non-bot chat messages with `session_id` and `addressed`; commands to the bot are not stored
- `bot_uses` – one row per served Gemini request (`username`, `kind`, `created_at`); the hourly quota counts it, `idx_bot_uses_user_time` serves that count
- `bot_interactions` – bot Q&A pairs with `session_id`
- `facts` – facts from the retired `!fact` / `!defact`. `username` is the **author**, not the subject, so `!who` / `!versus` find facts about the target by the mention: `storage.facts_naming()` takes those that name `@target` (LIKE, then a word boundary, so `@nick2` is not `@nick`) and passes them with their authors. `--build-memory` feeds facts with an `@nick` into that chatter's first profile and copies the rest into `knowledge`. Still read by `get_relevant_facts()` until the profiles are wired in, then dropped
- `chronicles` – memory: one row per finished conversation, `conversation` is its key (time of its first message in `BOT_TIMEZONE`, so the bot and the CLI agree whatever zone each runs in; `stream_chronicles` / `session_id` before `_migrate_memory()`), `first_id` / `last_id` – the `chat_messages` range it covers, `status` `ok` / `failed` / `skipped`
- `chatter_events` – memory: per-chatter lines from the chronicle
- `memory_state` – memory: `built` once `--build-memory` has finished the history; the bot leaves the memory alone until then
- `chatter_profiles` – memory: `portrait`, `relations` (JSON), `last_conversation`, `sessions_seen` (bot sessions); rewritten, never appended
- `knowledge` – manually imported lore, memes, stream history (unique per content). `source` – where a row came from (file name, `telegram:<chat>`, `facts`), so one source can be removed whole; the 96k rows imported before `source` existed have NULL. Index `idx_knowledge_source`
- `rolls` – one row per user per session, UPSERT on repeat roll. Holds current state, not throw history. `free_throws` counts free `!roll` throws, `curse_ceiling` / `curse_floor_at` / `curse_until` hold the curse (all added by `_migrate_rolls()` from `_ROLLS_COLUMNS`; old rows get 0 / NULL)
- `rewards` – action → Twitch custom reward id, so renaming a reward does not create a duplicate
- `roll_actions` – journal of redemptions: actor, raw input, target, old/new value, status. Duplicate guard and shield store
- `streams` – Twitch stream id → bot session, `started_at` / `ended_at` (`time.time()`). A known id means a restart, a new id shortly after the previous end means an outage – both keep the session
- `roll_perks` – perks of the previous stream: `(session_id, username, perk)` PK, `from_session`, `active_from` / `active_until` (countdown), `consumed` (curse already laid)
- `chat_fts` / `knowledge_fts` – FTS5 linked via `content=`, synced by triggers

Indexes created by `init_db()`: `idx_knowledge_content`, `idx_chat_messages_session`, `idx_bot_interactions_session`, `idx_chat_messages_username`, `idx_bot_interactions_username`, `idx_facts_username_fact`, `idx_chatter_events_user`, `idx_roll_actions_target`, `idx_knowledge_source`.

Session ID = **the stream** while the channel is live (`YYYY-MM-DD HH:MM` of its start, local time), otherwise the current date (`YYYY-MM-DD`), via `Bot.session_id` → `StreamTracker.session_id`. Chat, `!stat`, `!summary`, Gemini context and the game all use it. Old rows keep their date session ids; both formats sort chronologically as strings. A restart mid-stream resumes the same session through the `streams` table

Context of a free-text answer (in order), built by `src/gemini/answer_context.py`:
1. `[Сохранённые факты]` – asking user's own facts (always) + other users' facts matching prompt words
2. `[Память о людях]` – profiles of the asker and of nicks named in the question (up to 4); `[Хроника прошлого стрима]` – the previous stream's chronicle
3. `[Прошлый стрим]` – the whole previous stream (last session before this one with `MEMORY_CONVERSATION_MIN_MESSAGES`+ messages); during a stream only
4. `[Последние сообщения в чате]` – the whole current stream up to `CONTEXT_STREAM_MAX_MESSAGES` (2000, a safety cap; the longest stream had 861); offline the day's last `CONTEXT_CHAT_MESSAGES`
5. `[Контекст канала]` – FTS5 search across `knowledge` + `chat_messages` (all-time)
6. `[Язык чата]` – random sample from `knowledge` (always present)
7. `[Твоя реплика, на которую отвечают]` – on a reply to the bot (`reply_to_bot()`)
8. `prompts.memory_hint` when there is memory, then `{user} спрашивает: {prompt}`

**The fallback ladder:** Gemini's input filter judges the whole request by combinations of messages, and with two streams every fifth answer comes back blocked in the probe. `answer()` walks down while the request is blocked (`BLOCK_INPUT`, ~0.3 s each): two streams → whole current stream → last `CONTEXT_CHAT_MESSAGES` (the plain chat window, still with memory) → the same without memory, search and «language». An answer stopped by the random output filter (`BLOCK_OUTPUT`) is asked once more on the same rung; an answer with nothing in it (`EMPTY`) jumps to the last rung, so the worst case is that narrowest context. No answer at all (timeout, network, API error) ends the walk at once: it says nothing about the prompt, and another rung would only make the viewer wait a second full timeout. Measured on 7 hard questions × 2: 0 empty answers of 14 (the narrow context gives 2), ~$0.0056 and ~1.3 s per answer against $0.0011 and 0.9 s

## Key Notes

- **twitchio 3.x** – EventSub (WebSocket), not IRC. Requires `client_id` + `client_secret` from dev.twitch.tv. Dependencies are pinned in `requirements.in` (see Tooling). Its built-in command system is **switched off**: `Bot.process_commands()` is a no-op, because commands live in our own registry and twitchio would otherwise log `CommandNotFound` with a traceback for every `!…` message and every redemption. Component listeners receive the events independently
- **Bot token bootstrap** – if `TWITCH_BOT_TOKEN` + `TWITCH_BOT_REFRESH` set in `.env`, loaded in `setup_hook` via `add_token()`. First-time users do OAuth once to get values printed to console
- **channel:bot not needed** – bot is a moderator in the channel (`/mod botname`)
- **TWITCH_CHANNEL** – streamer's channel name, not the bot's own channel
- **Logging** – configured by `setup_logging()` in `src/core/logging_setup.py`, called from `run_bot()` (default `INFO`) and from each CLI branch (default `WARNING`). Override with `LOG_LEVEL`; set `LOG_FILE` for a rotating file. Startup, subscriptions, background task state and chunk sends are logged at INFO; errors use `logger.exception()` with tracebacks
- **Hot reload** – `CONTENT.md` is cached by mtime in `src/core/content.py` (`_ContentFile`) and re-read when the file changes. No restart needed. A file with no parsable sections, or missing a `REQUIRED` key, keeps the previous valid version and logs the error – renaming a required key therefore needs a restart, which the code using it needs anyway
- **DB connection** – single shared connection via `get_db()` (WAL + `synchronous=NORMAL`), closed via `close_db()` on shutdown. All queries serialize on it, so `asyncio.gather` over DB calls gives ordering, not parallelism
- **FTS5 sync** – FTS tables are linked via `content=` and kept in sync by SQLite triggers. `_migrate_fts()` rebuilds old-format tables; `_drop_legacy_objects()` removes the retired `interactions_fts` table and its triggers
- **Fact matching is Python-side** – SQLite `LIKE`/`lower()` only fold ASCII case, so Cyrillic facts are matched with `casefold()` in `_contains_ci()`. Relevant because `!fact` preserved the original case
- **Graceful shutdown** – SIGTERM/SIGINT via `loop.add_signal_handler()`, then `stop_background_tasks()` cancels all eight loops and waits for them – first thing in `Bot.close()`, before the HTTP session closes under loops still sending to chat – and `close_db()` runs from `finally`. After `close_db()` the database refuses to reopen (`get_db()` raises until `init_db()`): an event task that finishes late would otherwise open a fresh connection whose non-daemon thread keeps the process alive. The loops must go first: one waking up after `close_db()` calls `get_db()`, which opens a fresh connection and a new non-daemon aiosqlite thread, and the process never exits. **The handlers are installed twice** – once in `run_bot()` and again from `event_ready()` via `install_signal_handlers()`: twitchio starts its OAuth adapter as `web.AppRunner(..., handle_signals=True)` and aiohttp replaces whatever handlers were there, so the first set is dead from that moment. Without the second set the bot stops only through `asyncio.run()`'s emergency cleanup, with nothing in the log to say a signal arrived
- **Follow gate** – a viewer who does not follow the channel gets nothing but `texts.follow_required` (and `!help-bot`, so they can see what they are missing). Follower state is **not** a chat badge, so it comes from Helix (`fetch_followers(user=…)`, scope `moderator:read:followers`, the one the follow subscription already uses) through `FollowerCache` in `src/core/followers.py`: the answer is `bool(await followers.followers)` – `ChannelFollowers.followers` is an `HTTPAsyncIterator` with no `__bool__`/`__len__`, so testing it without awaiting is always true and the gate silently lets everyone through; `FOLLOW_CACHE_MINUTES` (15) TTL, invalidated on `event_follow`, and **fails open** – a silent Twitch must not lock the chat out. The hint repeats at most once per `FOLLOW_HINT_MINUTES` (10) per viewer, via a cooldown scope of its own. `FOLLOW_REQUIRED=false` turns the whole gate off
- **Hourly quota** – on top of the cooldown, and **only for `Kind.GEMINI`**: VIP `QUOTA_VIP_PER_HOUR` (60), everyone else `QUOTA_FOLLOWER_PER_HOUR` (30), broadcaster / moderator / subscriber unlimited, `0` = unlimited. The cooldown holds the pace, the quota holds the volume. Counted in SQLite (`bot_uses`, one row per served Gemini request, written **before** the call so a failed generation still counts) so a restart does not reset anyone. A handler that rejects malformed input calls `await ctx.refuse()` – it releases the cooldown *and* deletes the row, so a typo costs nothing. **On top of it sits a channel-wide ceiling**, `QUOTA_CHANNEL_PER_HOUR` (200, `0` = unlimited): the per-viewer quota bounds one person, not the bill, because every badge above follower has no quota at all – fifty followers alone are 1500 requests an hour. Counted by `count_channel_bot_uses(Kind.GEMINI, …)` over the same `bot_uses` window, checked before the personal quota, the broadcaster exempt. **Only the dispatcher's rows count**: `!who`, `!versus`, `!summary` and `!ascii` each write a second row for their own per-stream limit, so counting the whole table would charge those commands twice. Busiest hour on record: 14 served requests, so the default leaves about fourteen times the headroom. Exceeded – `texts.quota_channel` through `_deny()`, and only paid commands stop: `!roll`, `!rollstat` and `!stat` keep working
- **Cooldown** – expiry timestamps on `Bot._cooldowns`, keyed `scope:user`. **One ladder by viewer status for every command**: broadcaster / moderator / subscriber wait nothing, VIP waits `COOLDOWN_VIP`, everyone else `COOLDOWN_REGULAR` – resolved by `_cooldown_seconds()`, applied by the dispatcher, never by handlers. The scope is the command's **class**, so the two counters are independent: a wait on `!ask` does not block `!help-bot`. Free text addressed to the bot counts as `Kind.GEMINI` – it calls Gemini like `!ask` does. Status comes from `tier_of()` in `src/core/viewer.py`: broadcaster → moderator → subscriber (founder counts) → vip → regular, checked in that order so a VIP who also subscribes gets the gentler wait. Every status-dependent number – cooldown, quota, free throws, the per-stream limits of `!who` / `!versus` / `!summary` / `!ascii` – is picked from it by `by_tier()`, so a new badge is one edit there Refusals by **role and by quota** go through `ChatComponent._deny()`, which repeats at most once per `DENY_REPEAT_SECONDS` (30) per viewer in its own `DENY_SCOPE`: those answers never change, and a viewer without badges has no cooldown of their own, so the bot would otherwise reply to every single message. The cooldown message itself is deliberately not throttled – it carries the remaining seconds. Handlers call `ctx.clear_cooldown()` when they reject malformed input – it releases their own scope, so the scope cannot be mismatched. The dict is pruned once it exceeds 500 entries
- **Command matching** – exact match for plain entries; prefix entries require a word boundary, so `!whoever` does not match `!who`, while `!ask:вопрос` still does (separators: space, `:`, `,`)
- **Gemini client** – lazy init via `get_client()`. Semaphore `GEMINI_CONCURRENCY`, timeout `GEMINI_TIMEOUT`, and `GEMINI_RETRIES` retries with exponential backoff on transient errors (5xx, 429, network). **Timeouts are deliberately not retried** – the viewer is already waiting
- **Safety settings** – all 5 harm categories set to `threshold='OFF'`. Input-level filter is server-side and cannot be disabled
- **Output stop-list** – `passes_moderation()` blocks responses containing a word from `lists.banned` before they reach chat. Empty by default; matters because safety filters are off and proactive messages are unattended
- **Output hardening** – the chat is part of the model's context, so a viewer can plant text for the bot to repeat later. `defuse()` runs inside `Bot.send_chat_message()`, the one place every line the bot says on its own goes through – proactive remarks, chunks two and up, emotes, announcements – and strips a leading `/` or `.` so nothing reads as a chat command. The proactive remark, which nobody is watching, additionally goes through `strip_markdown()`, `fix_dashes()`, `strip_links()`, `strip_pings()` and `trim_to_sentence()`: otherwise it reaches chat almost raw, em dashes and all. `clean_nick()` cuts to `NICK_MAX` (25, a Twitch login's limit) because the answer echoes the nick back
- **Fallback retry** – free-text answers go down the ladder in `src/gemini/answer_context.py` (see the context list above), `!who`, `!versus` and `!summary` down their own rungs through the same `ladder.walk()`; no other handler retries on an empty answer
- **Thinking** – `GEMINI_THINKING_BUDGET`, default `0` (disabled). `-1` lets the model decide
- **Random knowledge sampling** – `get_random_knowledge()` keeps the list of all knowledge ids (~96k ints) and samples it directly, then fetches the rows by id: uniform and ~0.3 ms. A «random id → nearest row after it» scheme gives the row after a gap all of the gap's chances: once `--clear-lore --source` removes a big source, one line shows up in half the answers. The id list is re-read every `KNOWLEDGE_IDS_TTL` (600 s), so lore imported by the CLI while the bot runs reaches the sample without a restart; `invalidate_knowledge_cache()` resets it in the importing process
- **Probabilities are percentages** – `CAPS_PROBABILITY`, `EMOTE_PROBABILITY`, `PROACTIVE_TARGET_PROBABILITY`, `CONTEXT_SEARCH_KNOWLEDGE_SHARE` are `0..100`. A legacy fractional value like `0.3` is still accepted and logged as deprecated
- **CLI commands run `init_db()`** – including `--backup`. A new migration reaches the live DB the moment any CLI command runs, while the old bot process is still up. Keep migrations additive and harmless to the code that is currently running
- **Deployment** – Docker Compose, `restart: unless-stopped`. The image is built in two stages: dependencies are installed in `python:3.11-slim-bookworm` (the runtime's Debian, so a package built from source links against the glibc it runs on) strictly from `requirements.txt` with `--require-hashes`, and only they and the code move on to `gcr.io/distroless/python3-debian12` (118 MB against 209 MB for a single-stage slim build). Distroless has **no shell**, so `exec bot sh` does not work and the healthcheck is a Python one-liner rather than `test`/`stat`. Its entry point is Python itself, so the command is just the script path. Dependencies go to `/deps` on `PYTHONPATH`, deliberately **not** under `/app`: the tree is mounted at `/app` and would shadow them. `USER 1000:1000` (and `user: "1000:1000"` in compose) matches the host's ownership of the volumes – without the group the process ran as gid 0 and the database files on the volume went to root's group. The tree is mounted at `/app` **read-only**: it keeps `CONTENT.md` hot-reloading and the CLI working on the same files, while the bot cannot rewrite its own code or `.env`; the one command that writes to the tree, `--sync-emotes`, runs from the host venv. **No ports are published**: twitchio's OAuth adapter listens on `localhost` inside the container, so a published port never reached it. New tokens come from `make oauth`, which stops the container, runs the bot from the host venv in `data/` (where the container keeps `.tio.tokens.json`) and starts the container again after Ctrl+C – two processes on one refresh token would log each other out; the database, `.tio.tokens.json` and `heartbeat` live in `data/`. **Logs go to stdout only** (`LOG_FILE` empty): `docker logs` has the same content and the compose file rotates it (`json-file`, 10 MB × 5), not only the host's `daemon.json`, while a file sink is a second path that breaks silently when its mounted directory goes missing. `working_dir: /data` because twitchio writes its token file by a relative name. Session ids and memory keys use `BOT_TIMEZONE` (`Clock.ZONE`, default `Europe/Moscow`, formatted by `local_time()` in `utils.py`), not the process's zone, so the container, the host CLI and `make oauth` name one moment alike; an unknown name stops the start instead of falling back to UTC silently, as `TZ` does – the `Europe/Kiev` link no longer exists in current tzdata. `TZ=Europe/Moscow` stays in compose for the log timestamps only. `CMD` is exec-form so PID 1 is Python and `SIGTERM` reaches the signal handler. `_beat()` touches `BOT_HEARTBEAT` once a minute and the compose healthcheck reads its age: that is the one thing a restart policy cannot see, an alive process with a deaf bot
- **Tooling** – `pyproject.toml` holds tool config only (the bot is not an installable package). Dependencies follow the pip-tools convention: `requirements.in` lists the direct ones – every package the code imports, `aiohttp` included though twitchio brings it too – pinned, and `make lock` compiles it into `requirements.txt` with every transitive package and its hashes; the image installs only that file, with `--require-hashes`. `requirements-dev.in` (pytest, pytest-asyncio, ruff, pip-audit, pip-tools) compiles the same way into `requirements-dev.txt`, constrained by `-c requirements.txt`, so a package shared with the bot keeps the bot's version and the venv matches the image. Only the `.in` files are edited by hand. Ruff rules are in `pyproject.toml`: RUF001–003 are off (they flag the en dash and every Cyrillic letter), import sorting (`I`) and `ruff format` are not used, because both rewrap imports one name per line and break the aligned `add(...)` table in the dispatcher. mypy is not used: on this codebase it reports aiosqlite, twitchio and google-genai typing gaps, not bugs. `Makefile` holds the everyday commands (`venv`, `lint`, `fix`, `test`, `check`, `audit`, `lock`, `up`, `restart`, `logs`, `backup`)
- **Tests** – `tests/`, run by `make test` (`./venv/bin/python3 -m pytest`) on the host: the distroless image has no pytest. About 280 tests in under three seconds, with no network, no Gemini and no `.env`. `tests/conftest.py` sets `PYTHON_DOTENV_DISABLED=1` and fake required variables **before** anything from `src` is imported (config reads the environment at import time, and python-dotenv would otherwise find the live `.env`), points `BOT_DB_PATH` at a path that does not exist so a test without the `db` fixture fails loudly, and before every test recreates the module-level asyncio primitives (`database._db_lock`, `client._semaphore`, `game._lock`, `build._slots` / `_lock`), the `busy` sets of the per-stream limits and the caches: a lock binds to the first event loop that waits on it, and pytest-asyncio gives each test its own loop. `client.get_client()` raises, so a missing stub cannot become a Gemini bill – modules import `generate` / `generate_checked` by name, so a stub is patched where it is used (`ladder`, `commands`, `proactive`, `picture.command`, `memory.build`). `CONTENT.md` is replaced by one generated from `REQUIRED` whose values are the key names (`texts.help`), so tests assert which text was chosen, not its wording; it is swapped through `content._content`, because the file is bound at import. The `db` fixture gives an empty database with the full schema per test. `tests/fakes.py` holds `make_chatter()` (the five badges), `make_message()` and `FakeBot`. `test_content.py` also validates the real `CONTENT.md` – the cheapest check that a new text reached `REQUIRED`. Verification against a copy of the live DB is still manual

## Environment Variables

Required: `TWITCH_CLIENT_ID`, `TWITCH_CLIENT_SECRET`, `TWITCH_BOT_ID`, `TWITCH_CHANNEL`, `GEMINI_API_KEY`.

`.env.example` is the authoritative list (100 variables, grouped by section) – keep it in sync when adding config. Groups: Twitch credentials (incl. the optional broadcaster token), file paths and the zone (`BOT_DB_PATH`, `BOT_CONTENT_PATH`, `BOT_HEARTBEAT`, `BOT_TIMEZONE`; read in `config.py` like every other variable – `Files`, `Clock`), logging (`LOG_*`), Gemini (`GEMINI_*`), chat output (`CAPS_PROBABILITY`, `EMOTE_PROBABILITY`, `CHAT_MAX_CHUNKS`), cooldowns (`COOLDOWN_VIP` / `COOLDOWN_REGULAR`), Gemini quota (`QUOTA_*`), follow gate (`FOLLOW_*`), context (`CONTEXT_*`, incl. `CONTEXT_STREAM_MAX_MESSAGES` and the `CONTEXT_WHO_*` sample sizes), `!who` / `!versus` limits (`WHO_PER_STREAM_*`), `!summary` per stream (`SUMMARY_PER_STREAM_*`), memory (`MEMORY_ENABLED`, `MEMORY_SILENCE_MINUTES`, `MEMORY_CONVERSATION_MIN_MESSAGES`, `MEMORY_PROFILE_MIN_MESSAGES`), pictures (`PICTURE_*`), command reminder (`HELP_ANNOUNCE_ENABLED`, `HELP_ANNOUNCE_INTERVAL_MINUTES`), proactive (`PROACTIVE_*`), stream (`STREAM_RESUME_MINUTES`), roll (`ROLL_*`, incl. `ROLL_FREE_PER_SESSION`, `ROLL_PERKS_ENABLED`, `ROLL_PERK_MINUTES`), channel-points rewards (`REWARDS_ENABLED`, `REWARD_COST_*`, `REWARD_ATTACK_MAX_PER_USER`, `REWARD_CURSE_*`, `REWARD_REROLL_PROTECT_MINUTES`), emote spam (`EMOTE_SPAM_*`). The two chat loops take a **range**, `*_INTERVAL_MIN_MINUTES` / `*_INTERVAL_MAX_MINUTES`, parsed by `_interval_range()`; the old single `*_INTERVAL_MINUTES` still works and means a fixed interval, with a hint in the log. **No text belongs here** – it goes to `CONTENT.md`.

## When changing things

- **Dash: only `–` (en dash, U+2013).** The em dash (U+2014, deliberately not typed here) is not used anywhere in this project: not in `CONTENT.md`, `.env.example`, the docs, code comments or docstrings, and not in replies. Never add one. Check with `grep -rlP '\x{2014}'` over tracked files. `−` (U+2212) stays where it means minus, e.g. `75 − STEP`
- **Code comments and docstrings are in English.** Log messages, chat texts and the docs (`*.md`, `CONTENT.md`, `.env.example`) are in Russian. Russian chat words used as data examples (сосурян, «залупа стрима», НЕЛЬЗЯ/МОЖНО) stay as they are inside English comments
- **Comments and docs state the current state, not its history.** This applies to every comment, docstring, `<!-- … -->` note and line of documentation in the project.
  - **Forbidden:** dates (`2026-09-20`), attribution (`the owner asked`, `owner, 2026-09-19`, `found in review`, `at the owner's request`), change history (`used to be`, `was replaced on`, `before the fix`, `added on`), narrative of how a decision was reached, first person, rhetorical questions, conversational asides and jargon.
  - **Required:** the constraint, the invariant or the failure mode that makes the code what it is. A number that justifies a constant stays as a bare number, without who measured it or when.
  - **Length:** two or three lines for a comment. A docstring is one summary line, plus at most a short paragraph of constraints. Anything longer belongs in the docs, not next to the code.
  - Rewrite instead of deleting: `# The owner asked on 2026-09-15 to lower this from 5 to 3, because…` becomes `# Three throws: beyond that the points economy takes over`.
  - The one exception is `AUDIT.md`, a dated report where the dates are the subject.
  - Rationale that is genuinely long belongs in `BOT.md` or `README.md` as a statement of how the thing works, still without the history of how it got there.
- **Docs are part of the change, not a follow-up.** Every change to behaviour, config, schema or layout updates the affected docs in the *same* turn, before reporting the work as done: `CLAUDE.md` (this file), `README.md`, `BOT.md`, `.env.example`, and the `<!-- … -->` notes in `CONTENT.md`. A change that is only documented in the commit message is unfinished
- Adding a command: one `add()` line in `ChatComponent.__init__` + a handler in the right package (see "Where code goes") + its texts in `## texts` of `CONTENT.md` and in `REQUIRED` (`src/core/content.py`). Then update **all three**: `CLAUDE.md`, `README.md` (command table) and `BOT.md` (registry table)
- Adding config: `src/core/config.py` (with a validated `_env_*` helper) + `.env.example` + README env table. If it is a *text*, it is not config – put it in `CONTENT.md`
- Adding a text: `CONTENT.md` + `REQUIRED` in `src/core/content.py`. Never inline a chat-visible string in a handler
- Editing `CONTENT.md` while the bot runs: the running process hot-reloads it and renders it with **its own, old** code. Adding a placeholder to an existing key before the restart makes `safe_format()` fail and the raw template (`@{user} выбил {value}…`) goes to chat. Add a new key instead
- Changing rewards: title/prompt in `CONTENT.md`, cost/limit in `.env` – both reach Twitch only on restart. Never create the rewards by hand in the dashboard
- Changing the DB schema: `init_db()` must stay idempotent – it runs on every start against a live 90-session database
