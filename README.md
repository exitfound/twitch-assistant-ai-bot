# Twitch AI Bot

Twitch-бот для работы в чате канала на Twitch. Генерирует ответы через **Gemini 2.5 Flash**. Хранит полную историю чата в SQLite с полнотекстовым поиском (FTS5) и долговременной памятью между стримами (опционально).

- Python 3.11+
- [twitchio](https://github.com/TwitchIO/TwitchIO) 3.x – подключение к Twitch через EventSub (WebSocket), не IRC
- [google-genai](https://pypi.org/project/google-genai/) – Gemini API (модель `gemini-2.5-flash`)
- [aiosqlite](https://github.com/omnilib/aiosqlite) – асинхронная работа с SQLite в WAL-режиме
- [python-dotenv](https://pypi.org/project/python-dotenv/) – загрузка переменных окружения из `.env`

## Установка

### 1. Создать бот-аккаунт на Twitch

Зарегистрируй отдельный Twitch-аккаунт, который будет выступать ботом (например `securityexpert`). Это обычный аккаунт – специальной регистрации «как бот» не требуется. После создания аккаунта зайди в чат стримерского канала (под стримерским аккаунтом) и дай боту права модератора:

```
/mod botname
```

Модератор нужен чтобы бот мог писать в чат без ограничений Twitch по rate-limit. Делается один раз – разрешение хранится на стороне Twitch и сохраняется при переносе бота.

### 2. Создать приложение на dev.twitch.tv

1. Зайди на [dev.twitch.tv/console/apps](https://dev.twitch.tv/console/apps) под **бот-аккаунтом**
2. **Register Your Application**:
   - **Name** – любое название
   - **OAuth Redirect URLs** – `http://localhost:4343/oauth` (twitchio поднимает локальный сервер на этом порту для OAuth-flow)
   - **Category** – Chat Bot
3. После создания зайди в **Manage** → скопируй **Client ID**
4. Нажми **New Secret** → скопируй **Client Secret** (показывается один раз)

### 3. Узнать числовой ID бот-аккаунта

Twitch API работает с числовыми user ID, а не с никами. Узнать ID бот-аккаунта можно здесь: [streamweasels.com/tools/convert-twitch-username-to-user-id](https://www.streamweasels.com/tools/convert-twitch-username-to-user-id/) – введи ник бота, скопируй числовой ID.

### 4. Получить Gemini API Key

Зайди на [aistudio.google.com](https://aistudio.google.com/) → **Get API key** → создай ключ. Бесплатного тарифа достаточно для минимальной работы бота в чате.

### 5. Установить зависимости

```bash
git clone https://github.com/exitfound/twitch-assistant-ai-bot
cd twitch-assistant-ai-bot
python3.11 -m venv venv
./venv/bin/pip install --require-hashes -r requirements.txt
```

Нужен именно Python 3.11 – на нём работает образ. Для разработки вместо этого `make venv`: тот же venv плюс pytest, ruff и pip-audit из `requirements-dev.txt`.

### 6. Настроить .env

```bash
cp .env.example .env
```

Заполни обязательные переменные (подробности в секции [Переменные окружения](#переменные-окружения)):

```env
TWITCH_CLIENT_ID=...
TWITCH_CLIENT_SECRET=...
TWITCH_BOT_ID=...
TWITCH_CHANNEL=...
GEMINI_API_KEY=...
```

`TWITCH_CHANNEL` – ник стримера (канал, в котором бот будет работать), **не** ник самого бота.

`TWITCH_BOT_TOKEN` и `TWITCH_BOT_REFRESH` пока оставь пустыми – они будут получены при первом запуске.

### 7. Первый запуск – OAuth-авторизация

Авторизация идёт **на хосте, не в контейнере**: OAuth-адаптер twitchio слушает `localhost` внутри контейнера, и снаружи до него не достучаться, поэтому порт 4343 в compose не публикуется. Бот запускается из venv в каталоге `data/` – там же контейнер держит `.tio.tokens.json`:

```bash
make oauth        # остановит контейнер, запустит бота на хосте, после Ctrl+C поднимет контейнер обратно
```

Без `make` – то же руками: `docker compose stop bot`, затем `cd data && BOT_DB_PATH=chat_history.db ../venv/bin/python3 ../bot.py`, после входа `Ctrl+C` и `docker compose start bot`. Контейнер на время входа останавливается обязательно: refresh-токен одноразовый, и два процесса на одной паре токенов разлогинят друг друга.

Без токена бот не подключится к чату и выведет ссылку:

```
[WARNING] __main__: Похоже, нет токена бота или у него не те права. Открой в браузере и войди под аккаунтом бота:
http://localhost:4343/oauth?scopes=user:read:chat+user:write:chat+user:bot&force_verify=true
(в контейнере ссылка не откроется – запусти make oauth на хосте)
```

Открой эту ссылку в браузере. Войти нужно именно **под бот-аккаунтом**, не под стримерским. Разреши запрошенные права. После успешной авторизации twitchio перехватит callback, запишет токен в `.tio.tokens.json` (права 600) и напишет в лог последние четыре символа и имя переменной для `.env`, например `TWITCH_BOT_TOKEN`: сам токен в лог не попадает. Перенеси значения из файла в `.env` и останови бота (`Ctrl+C`).

Эта процедура делается **один раз**. В дальнейшем twitchio автоматически обновляет access token через refresh token. Обновлённые токены сохраняются в файл `.tio.tokens.json` (в .gitignore) – это внутренний механизм twitchio.

### 7а. Токен канала для наград за баллы (опционально)

Для [наград за баллы канала](#награды-за-баллы-канала) нужен второй токен – **владельца канала**: управлять наградами Twitch разрешает только ему, прав модератора у бота для этого мало. Канал должен быть компаньоном или партнёром.

Пока токена нет, бот при запуске пишет в лог ссылку:

```
[WARNING] __main__: Награды за баллы канала выключены: нет токена канала. Открой в браузере и войди под аккаунтом канала channelname:
http://localhost:4343/oauth?scopes=channel:manage:redemptions&force_verify=true
```

Ссылка открывается так же, как для бота, – с хоста, через `make oauth`. Открой её и войди **под аккаунтом стримера**. Награды включатся сразу, перезапуск не нужен. Токен ляжет в `.tio.tokens.json`, а в логе будут имена переменных `TWITCH_BROADCASTER_TOKEN` и `TWITCH_BROADCASTER_REFRESH` – перенеси значения из файла в `.env`. Если не успел, при штатной остановке twitchio сохранит токен в `.tio.tokens.json`, и следующий запуск возьмёт его оттуда. Но если бот будет убит без штатной остановки (`kill -9`, пропало питание), файл не запишется – поэтому `.env` надёжнее. Если награды не нужны вовсе – `REWARDS_ENABLED=false`, и ссылка перестанет появляться.

### 8. Запуск

Боевой способ – Docker Compose:

```bash
docker compose up -d          # собрать при необходимости и поднять
docker compose logs -f        # смотреть логи
docker compose restart bot    # перезапустить
docker compose down           # остановить
```

`restart: unless-stopped` поднимает бота после падения и после перезагрузки машины. Обслуживающие команды выполняются в том же образе:

```bash
docker compose run --rm bot /app/bot.py --backup /data/copy.db
```

Запуск без контейнера годится для отладки:

```bash
./venv/bin/python3 bot.py
```

Успешный запуск выглядит так:

```
[INFO] __main__: Бот запущен | Ник: botname | Сессия: ГГГГ-ММ-ДД
[INFO] __main__: Подписка на чат #channelname
[INFO] __main__: Подписка на фоловы
[INFO] __main__: Подписка на начало и конец эфира
[INFO] __main__: Проактивные сообщения включены (раз в 5–30 мин)
[INFO] __main__: Оповещения о снятии проклятий включены
```

Бот запущен и слушает чат. Для остановки – `Ctrl+C` или `SIGTERM`. При остановке корректно закрывается соединение с БД.

Уровень логирования задаётся `LOG_LEVEL` (по умолчанию `INFO` для бота и `WARNING` для CLI-команд). Чтобы писать логи ещё и в файл с ротацией, укажи `LOG_FILE=bot.log`.

**Примечание:** подписка на follow-события требует scope `moderator:read:followers`. Если при запуске появляется ошибка, переавторизуйте бота по ссылке из консоли.

## Использование в чате

### Триггеры

Команды (`!who`, `!ask` и остальные) работают просто написанные в чат – обращаться к боту для них не нужно. На свободный текст бот реагирует только в трёх случаях:

1. **Слова на `сосур*` или `secur*`** – любое слово, начинающееся с `сосур` (сосурян, сосурити, сосуряночка) или с латинского `secur` (securityexpert, security). Регулярное выражение: `(?:сосур|secur)\w*` (регистронезависимое). Бот найдёт триггер в любом месте сообщения.
2. **`@securityexpert`** – прямое упоминание бота в сообщении (регистронезависимое).
3. **Реплай на сообщение бота** – ответ на любое предыдущее сообщение бота через функцию «Reply» в Twitch-чате.

Все три триггера эквивалентны. После срабатывания триггера бот извлекает текст вопроса: убирает из сообщения упоминание `@securityexpert` и слова на `сосур*` / `secur*`, оставшийся текст отправляет как промпт. Если после очистки текст пустой – отправляет исходное сообщение целиком.

### Команды

Команда пишется в чат как есть: `!who nick`, `!ask что такое FTS5`, `!roll`. Через обращение тоже работает: `@securityexpert !stat`, `сосурян !help-bot`, реплай на бота с `!roll`. Аргументы голой команды берутся как написаны, поэтому `!who securityexpert` находит ник бота, а не срезает его как обращение.

| Команда | Что делает |
|---|---|
| `!help-bot` | Перечисляет команды – без описаний и без пометок о правах: что делает каждая, расписано в описании под стримом, в 450 символов сообщения это уже не влезает. Имя с суффиксом, чтобы не пересекаться с `!help` других ботов в чате |
| `!stat` | Одним сообщением: сначала свои цифры за стрим и за всё время, затем итог стрима, затем канал за всё время. Команды к боту в числа не входят: считается живой диалог и обращения к боту свободным текстом |
| `!stat <ник>` | То же про другого зрителя: сколько написал в этом стриме, за всё время и сколько раз обращался к боту |
| `!roll` | Бросает кубик 1–100. Кто набрал меньше всех в текущей сессии – подзалупный китежанин стрима, кто больше всех – достойнейший китежанин стрима. Каждый новый ролл перезаписывает предыдущий результат игрока. Бесплатно – 3 броска за сессию, дальше [за баллы канала](#награды-за-баллы-канала). Стример катает без лимита. Пока стрим оффлайн, игра закрыта |
| `!rollstat` | Показывает, как стоят дела в игре: твой бросок в этом эфире и сколько бесплатных осталось, проклятие или щит, если есть, а следом кто сейчас подзалупный китежанин стрима и кто достойнейший. Ничего не бросает и ничего не меняет. Пока стрим оффлайн, игра закрыта |
| `!ascii <ссылка>` | Рисует картинку по ссылке символами Брайля – одним сообщением в чат. **Только для подписчиков, VIP, модераторов и стримера**, с лимитом за эфир: VIP 3, подписчики и модераторы 10, стример без ограничений. Ссылка обязательна: без неё бот просит её указать. Перед показом Gemini смотрит, что на картинке, и запрещённое рисовать отказывается. Описание в чат не идёт – бот его запоминает и пишет в лог, но вслух не комментирует |
| `!ask <вопрос>` | Фактический ответ без персонажа бота. Gemini отвечает как обычная модель – без системного промпта, plain text, до 2 сообщений подряд. Понимает уточнения к своему прошлому ответу в течение 15 минут |
| `!summary` | Саммари текущего стрима целиком: основные темы и пара самых зашкварных моментов с цитатами. `!summary прошлый` или `!summary` вне эфира – прошлый стрим. За эфир: фолловер 1, VIP 3, сабы и модеры 10, стример без лимита (текущий и прошлый считаются вместе). До 2 сообщений |
| `!who <ник>` | Горсть фактов про юзера вперемешку и пара подколов. Каждый раз из новой случайной выборки всей его истории (события из памяти бота, сообщения с разных стримов, с кем общается), поэтому ответы не повторяются. Команды зрителя не учитываются, только живой диалог. За эфир: фолловер 1, VIP 3, сабы и модеры 10, стример без лимита |
| `!versus <ник1> <ник2>` | Батл двух юзеров: бот накидывает факты про каждого из случайной выборки всей истории, высмеивает, называет проигравшего (чьи факты тупее) и прожаривает обоих. До двух сообщений подряд. За эфир: фолловер 1, VIP 3, сабы и модеры 10, стример без лимита. Если про один из ников бот ничего не знает, он отказывается, а не выдумывает |
| Любой другой текст | Отправляется как вопрос в Gemini вместе с контекстом |

### Классы команд

Команды делятся на два класса, и класс же определяет, в каком счётчике лежит кулдаун:

| Класс | Команды | Чем обслуживается |
|---|---|---|
| **локальные** | `!help-bot`, `!stat`, `!roll`, `!rollstat` | SQLite и текст из `CONTENT.md` – отвечают мгновенно и ничего не стоят |
| **Gemini** | `!ascii`, `!ask`, `!summary`, `!who`, `!versus` и любое свободное обращение к боту | Запрос к Gemini API: деньги, ожидание до минуты, место в семафоре |

Счётчики независимы: пока висит пауза после `!ask`, нажать `!help-bot` можно.

### Кулдаун

Одна лесенка по статусу зрителя – на оба класса и на все команды без исключений:

| Статус | Пауза | Обращений к Gemini в час | Бесплатных роллов за стрим |
|---|---|---|---|
| Стример | нет | без лимита | без лимита |
| Модератор | нет | без лимита | 10 |
| Подписчик / фаундер | нет | без лимита | 10 |
| VIP | `COOLDOWN_VIP` (10 сек) | `QUOTA_VIP_PER_HOUR` (60) | 5 |
| Фолловер | `COOLDOWN_REGULAR` (30 сек) | `QUOTA_FOLLOWER_PER_HOUR` (30) | 3 |
| Не фолловер | – | бот не отвечает | – |

Пауза держит темп, часовая квота – объём: она считает только запросы к Gemini (`!ask`, `!summary`, `!who`, `!versus`, свободный текст), потому что они стоят денег. Локальные команды ограничивает только пауза. Счётчик лежит в таблице `bot_uses`, поэтому перезапуск бота никому квоту не обнуляет, а отказ по формату (`!who` без ника) возвращает и паузу, и место в квоте.

**Без фолова бот не отвечает.** Незафоловленный зритель получает только предложение зафоловиться (не чаще раза в `FOLLOW_HINT_MINUTES`) и может посмотреть `!help-bot` – больше ничего. Фолловер ли человек, бот спрашивает у Twitch и помнит ответ `FOLLOW_CACHE_MINUTES` минут; если Twitch не ответил, зритель считается своим. Выключается через `FOLLOW_REQUIRED=false`.

Оплаченная подписка и значок модератора снимают кулдаун полностью – для них значений в конфиге нет, это правило. Если человек одновременно VIP и подписчик, применяется более щадящий вариант (подписчик).

Кулдаун ставит диспетчер, а не обработчик, – **до** сбора контекста и вызова Gemini API, чтобы быстрый спам не успевал запустить несколько генераций подряд. Если команда отвергает кривой ввод (например, `!who` без ника), кулдаун снимается обратно.

При срабатывании бот отвечает сообщением с оставшимся временем ожидания: `texts.cooldown_local` или `texts.cooldown_gemini` – в зависимости от класса.

### Обработка `!ask`

`!ask` работает иначе: Gemini вызывается **без** системного промпта (`prompts.system`) и без контекста чата/knowledge. Вместо этого берётся отдельная инструкция `prompts.ask`: модель знает, что отвечает зрителю в чате Twitch, и должна уложиться в 700 символов plain text. Температура своя, `GEMINI_ASK_TEMPERATURE` (0.5): на температуре болтовни модель чаще выдумывает факты. Вопрос уходит в модель в исходном регистре. Если тот же зритель спрашивал за последние 15 минут, в запрос добавляется его прошлый вопрос и ответ (`prompts.ask_followup`) – так работают уточнения вроде «а подробнее?». Ответ очищается от маркдауна, обрезается до 850 символов по концу предложения и отправляется **не больше чем в двух сообщениях** по 450 символов с паузой 1.5 сек. Первое сообщение – reply (со значком «Чат-бот»), остальные – как продолжение.

### Обработка ошибок Gemini

Входной фильтр Gemini не отключается и оценивает весь запрос целиком: чем больше в нём чата, тем чаще он срабатывает. Поэтому заблокированный ответ на обращение повторяется **лестницей**, каждый раз с меньшим контекстом: два стрима → весь текущий стрим → последние `CONTEXT_CHAT_MESSAGES` сообщений → то же без памяти, `[Язык чата]` и `[Контекст канала]`. Заблокированный запрос возвращается за доли секунды, так что ступень почти не добавляет времени. Пустой ответ без блокировки сразу идёт на последнюю ступень. Если Gemini не ответил вовсе (таймаут, сеть, ошибка API), лестница на этом заканчивается: дело не в запросе, и ещё одна ступень только удвоила бы ожидание. Если пусто и на последней ступени – бот отвечает «не удалось получить ответ».

## Проактивные сообщения

Бот периодически пишет в чат без запроса. Контролируется через `PROACTIVE_ENABLED` и диапазон пауз `PROACTIVE_INTERVAL_MIN_MINUTES` / `PROACTIVE_INTERVAL_MAX_MINUTES`.

- Бот пишет только в живой разговор: если с его прошлой реплики никто в чате не написал, реплика пропускается. Команды боту разговором не считаются
- Пауза до каждой реплики берётся случайно между `PROACTIVE_INTERVAL_MIN_MINUTES` (5) и `PROACTIVE_INTERVAL_MAX_MINUTES` (30): ровный интервал читается как расписание
- Если чат пустой (нет сообщений в текущей сессии) – пропускает
- С вероятностью `PROACTIVE_TARGET_PROBABILITY` обращается к случайному активному пользователю из последних `PROACTIVE_ACTIVE_WINDOW` сообщений, иначе – общий комментарий
- Использует полный контекст: `[Последние сообщения в чате]` + `[Язык чата]`
- CAPS с вероятностью `CAPS_PROBABILITY`
- С вероятностью `EMOTE_PROBABILITY` добавляет случайный эмот в конец сообщения
- Отправляется через HTTP API (без reply-контекста)

## Эмоты

### Список эмотов

Хранится в `CONTENT.md`, ключ `lists.emotes` – один эмот на строку, `#` для комментариев. Поддерживает hot-reload без перезапуска бота.

Список ведётся не руками: `--sync-emotes` тянет эмоты канала через Twitch Helix API и дописывает недостающие, разложив по группам (фолловерские, сабские по тирам, за биты). Повторный запуск ничего не дублирует. Источник `global` добавляет ~300 глобальных эмотов Twitch – учитывай, что тогда эмоты канала будут выпадать заметно реже.

**Важно про отображение:** эмот отрендерится, только если он доступен *отправителю*. Сабские эмоты канала бот покажет картинкой, лишь когда бот-аккаунт оформит подписку нужного тира (tier 3 открывает все), фолловерские – когда бот зафоловлен. Иначе в чат уйдёт просто текст кода.

Сейчас в файле лежат глобальные эмоты Twitch и эмоты канала, подтянутые через `--sync-emotes`: фолловерские и сабские tier 1/2/3. Эмоты из BTTV/7TV/FFZ добавляются вручную – у канала их нет, поэтому автоматической подтяжки в проекте нет.

### Случайный эмот в ответах

С вероятностью `EMOTE_PROBABILITY` бот добавляет случайный эмот из `lists.emotes` в конец обычных ответов Gemini (`handle_default`, `!who`, `!versus`, проактив).

### Спам эмотами

Если `EMOTE_SPAM_ENABLED=true` – бот через случайную паузу от `EMOTE_SPAM_INTERVAL_MIN_MINUTES` до `EMOTE_SPAM_INTERVAL_MAX_MINUTES` минут самостоятельно отправляет в чат от `EMOTE_SPAM_MIN` до `EMOTE_SPAM_MAX` случайных эмотов (независимый фоновый цикл, аналогично проактивным сообщениям). Только во время эфира и только если с прошлой порции кто-то написал в чате: в пустой чат эмоты не летят.

## Картинки в брайль-арт

Команда `!ascii <ссылка>` берёт картинку по ссылке и рисует её в чате символами Брайля – одним сообщением.

Почему брайль, а не обычный ASCII. Чат Twitch рисуется пропорциональным шрифтом, поэтому строки из `.:-=+*#%@` разъезжаются, а подряд идущие пробелы схлопываются – половина арта просто исчезает. Символы Брайля (U+2800–U+28FF) рендерятся одинаковой ширины, пустой символ U+2800 пробелом не считается и не схлопывается, а плотность вчетверо выше: одна ячейка несёт матрицу 2×4 точки.

Почему всё влезает в одно сообщение. Строка брайля не содержит пробелов – для браузера это одно неразрывное слово. Пробелы стоят только на стыках строк, перенос идёт строго по ним, поэтому каждая строка сама ложится на свою визуальную строку. Переводов строки в сообщении Twitch не бывает, и они не нужны. Ник отправителя ничего не сдвигает: первая строка арта целиком не влезает в остаток первой визуальной строки и уезжает на вторую.

Отсюда и размер: бюджет считается не в строках, а в символах сообщения. Строка из N символов стоит N+1 вместе с разделителем, поэтому рамка под картинку подбирается по её пропорциям – высокой выгоднее меньше колонок и больше строк. Ширина ограничена `PICTURE_MAX_COLS` (26): строка должна влезать в колонку чата целиком, иначе порвётся переносом. Внутри рамки картинка переводится в серый, обрезается по содержимому и растягивается по контрасту. Дальше – порог. Сначала пробуется обычный, общий на всю картинку: на контрастном рисунке он даёт самые чистые линии. Но одно число не справляется, когда большая область лежит чуть темнее него: зелёный Pepe целиком уходит в чернила и остаётся силуэт без морды. Поэтому если доля закрашенных точек вышла больше 45% или меньше 5%, включается локальный порог – точка сравнивается не с общим числом, а со своим окружением, и внутри крупных однотонных пятен проступают контуры и черты. Дизеринг не используется вовсе: на шестидесяти точках в ширину он даёт шум, а не полутона.

Отдельно обрабатывается прозрачность. Вырезанная картинка на прозрачном фоне сама по себе формы не даёт: золотой кубок, положенный на белое, по яркости почти белый – порог его теряет, и остаётся путаница штрихов; у пингвина Tux по той же причине пропадает белый живот. Зато канал прозрачности знает форму точно, поэтому по нему обводится силуэт и добавляется к рисунку, а обрезка полей делается по нему же. Если прозрачность в файле есть, но по факту непрозрачна целиком, обводить нечего и она игнорируется.

Дальше заливка **выедается** (`PICTURE_HOLLOW`): из рисунка вычитается он же, ужатый на одну точку, и остаются только края. Сплошное чёрное пятно теряет форму – фотография енота выходит кляксой с контуром по краю, – а тонкие линии не страдают, они сами состоят из края, поэтому рисованному Pepe выедание ничего не делает. Поверх контура возвращаются самые тёмные места (темнее `PICTURE_SHADOW`, 45): с одной стороны тень залита, с другой идёт контур – это и даёт объём вместо проволочной схемы.

Ещё одна поправка – `PICTURE_ASPECT` (0.8): ячейка чата выше, чем вдвое своей ширины, поэтому точка брайля не квадратная и картинка без сжатия по вертикали выглядит вытянутой. Число подбирается под то, как чат рисует шрифт; меньше 1 – сжать сильнее.

Что получается: узнаваемы логотипы, эмоуты, силуэты, крупные лица. Фотографии и скриншоты – нет, точек слишком мало. У зрителя с сильно растянутым чатом арт может разъехаться: в одном сообщении нет способа поставить принудительный перенос.

Команда открыта со значка подписчика: фолловеру и не фолловеру она недоступна вовсе. За эфир VIP может нарисовать `PICTURE_PER_STREAM_VIP` (3) картинки, подписчик и модератор – `PICTURE_PER_STREAM_SUB` (10), стример не ограничен. Счёт ведётся в журнале `bot_uses` с момента начала эфира, поэтому перезапуск бота лимит не обнуляет; вне эфира окно – сутки. Считаются только показанные картинки: любой отказ лимита не стоит, а вот повтор из кэша стоит – зритель всё равно занял чат картинкой. Рисуется одна картинка зрителя за раз: пока первая скачивается и проверяется, повторные `!ascii` от него молча отбрасываются. Иначе у подписчика, у которого нет ни кулдауна, ни квоты, пять команд подряд прошли бы проверку лимита с одним и тем же счётчиком.

Ссылка пишется в самой команде: `!ascii https://…`. Без неё бот просит указать ссылку – последнюю ссылку из чата он не подставляет: угадывание приносит не ту картинку.

Готовые арты кэшируются по ссылке – тридцать две последних, в памяти, до перезапуска. Чат по природе повторяется, и повтор не стоит ни скачивания, ни отрисовки, ни запроса к Gemini. Вердикт кэшируется вместе с артом, поэтому одобренная ссылка остаётся одобренной до конца эфира. Часовую квоту повтор всё равно тратит: она ограничивает, как часто зритель заставляет бота действовать, а не во сколько это обходится.

В Gemini уходит уменьшенная копия, 512 пикселей по длинной стороне: модели надо лишь понять, что нарисовано, и решить, можно ли это показывать – разрешение на такое решение не влияет, а на фотографии это срезает около 90% объёма.

Описание бот запоминает – оно пишется в `bot_interactions` с пометкой `[ascii]`, поэтому попадает в контекст и бот может говорить о показанном позже. Вслух в момент отправки он ничего не комментирует.

Ссылку даёт зритель, поэтому проверок больше, чем кода: только `http`/`https`, каждый адрес хоста проверяется на публичность (ссылка на внутренний адрес превратила бы бота в способ стучаться по локальной сети хозяина), переадресации обходятся вручную с той же проверкой на каждом шаге, содержимое обязано быть `image/*`, размер ограничен `PICTURE_MAX_BYTES`, распакованный – 40 мегапикселями, и он проверяется по заголовку файла до раскодирования, а не после.

Проверки имени при этом мало: httpx резолвит его второй раз, и запись с нулевым TTL отдала бы публичный адрес на проверку и локальный на скачивание. Поэтому проверяется ещё и адрес, с которым соединение установлено на самом деле.

Gemini здесь не рисует: рисование детерминированное, из пикселей. Он смотрит на картинку и либо запрещает её показывать (`PICTURE_CHECK`), либо коротко описывает. **Отказ закрытый**: если вердикта нет – таймаут, сбой сети или сам Gemini отказался говорить про эту картинку, – она не показывается. Неудачная проверка не кэшируется, поэтому повтор может пройти. Закрыт отказ и по форме ответа: картинка показывается, только если ответ начинается со слова `МОЖНО`. Всё остальное – `НЕЛЬЗЯ`, «извини, но нельзя», любой непонятный ответ – считается запретом. Непонятный ответ при этом не кэшируется, так что повтор может пройти.

Это единственное место в проекте, где **фильтры безопасности Gemini включены**: откровенный и опасный контент блокируются с порога `BLOCK_MEDIUM_AND_ABOVE`, а оскорбления и ненависть не фильтруются – из них сделаны мемы. Везде ещё фильтры выключены намеренно, иначе не работает персонаж, но здесь задача обратная: бот не разговаривает, а проверяет. Классификатор Google становится вторым слоем помимо промпта – на картинку, которую он обсуждать не станет, ответа не придёт вовсе, а это уже отказ. В чат описание не идёт – картинка говорит сама за себя, а реплика следом забивает чат, – оно пишется в лог, по которому видно, что зрители таскают по ссылкам.

## Напоминание о командах

Раз в `HELP_ANNOUNCE_INTERVAL_MINUTES` (30) бот сам пишет в чат, что умеет: список команд, как его позвать свободным текстом и куда смотреть за описанием. Зритель, зашедший посреди эфира, иначе про команды не узнает – справку нужно сначала догадаться спросить.

Напоминание уходит, только если с прошлого в чате кто-то писал: в заглохший чат бот сам себе не рекламирует, и два одинаковых сообщения подряд не выходят. Если за это время кто-то уже вызвал `!help-bot`, список и так был в чате – напоминание пропускается. Сами команды в базу не пишутся, так что активностью чата считается только живой диалог.

Текст – ключ `help_announce` в `CONTENT.md`, правится на лету. Сообщение общее, без ника, и в `bot_interactions` не пишется: это объявление, а не ответ.

Напоминание уходит только **пока идёт эфир** и только если в чате кто-то писал: пустому чату рекламировать нечего. Выключается через `HELP_ANNOUNCE_ENABLED=false`.

## Игра «залупа стрима»

`!roll` бросает кубик `ROLL_MIN`–`ROLL_MAX`. Кто за сессию выбросил меньше всех – тот и залупа. В таблице `rolls` на игрока приходится одна строка за сессию (`UNIQUE(session_id, username)`), повторный бросок перезаписывает её через UPSERT – таблица хранит текущее состояние, а не историю бросков.

Бесплатных бросков – `ROLL_FREE_PER_SESSION` (3) за сессию, счётчик лежит в той же строке (`free_throws`). Сколько осталось, бот дописывает к каждому ответу `!roll`. Когда бесплатные кончились, ролл не меняется, а бот отвечает, что дальше – награда за баллы канала.

**Стример катает без лимита** и без приписки об остатке. Его броски всё равно идут в счётчик, поэтому доп. ролл за баллы у него работает так же, как у всех.

Титул нигде не лежит: он **вычисляется** при каждом обращении запросом «минимум сессии», где ничья разруливается по времени броска, а совсем полная ничья – по `id`, чтобы ответ не плавал от запроса к запросу.

`!rollstat` показывает то же самое, но ничего не бросая: свой бросок и остаток бесплатных, проклятие с его потолком и сколько до снятия, щит за баллы или щит китежанина прошлого стрима, а в конце – текущие залупа и китежанин. Команда только читает: перк-щит от неё не активируется, счётчики не двигаются.

Рядом с залупой – **китежанин стрима**: самый высокий ролл сессии, считается тем же способом, только наоборот. Бот дописывает «Достойнейший китежанин стрима: @nick (97 из 100).» к ответам `!roll` и к итогам наград, которые меняют ролл. Если китежанин и залупа – один человек (катал один игрок или у всех одно число), китежанин не показывается.

### Награды за баллы канала

Сверх бесплатных бросков и для саботажа – четыре награды в меню баллов канала. Бот создаёт их в Twitch сам, сам применяет и сам подтверждает: ни стримеру, ни зрителю нажимать ничего не нужно. Нужен [токен канала](#7а-токен-канала-для-наград-за-баллы-опционально).

| Награда | Цена по умолч. | Ввод | Что делает |
|---|---|---|---|
| ДОПОЛНИТЕЛЬНЫЙ ROLL | 100 | – | Бросок за себя. Бесплатные броски не тратит |
| ПЕРЕБРОС ЧУЖОГО ROLL | 250 | ник | Бот бросает за жертву, новое число заменяет её ролл. Можно и за того, кто ещё не катал, – бросок введёт его в игру. После переброса жертва 3 минуты неуязвима для новых перебросов |
| ПРОКЛЯТИЕ НА ROLL | 1000 | ник | **Пробивает щит.** Бросок жертвы не выше 75, каждый её следующий бросок опускает потолок на 5, до 25. На 25 потолок держится 15 минут, потом проклятие спадает |
| ЩИТ ОТ ЧУЖОГО ROLL | 500 | – | Переброс на тебя не действует до конца сессии. От проклятия не спасает |

Итог бот пишет в чат:

```
@carol проклял @bob и ему выпало 36 из 75, дальше потолок 70 и падает на 5 с каждым новым броском. Подзалупный китежанин стрима: @bob (36 из 100).
@bob выбил 11 из 70 под проклятием – подзалупный китежанин стрима! (бесплатных осталось 1) (следующий потолок 65)
```

Проклятие держится в строке жертвы (`curse_ceiling`, `curse_floor_at`, `curse_until` в `rolls`) и снимается само: как только потолок пробыл на дне 15 минут – тогда бот пишет в чат, что проклятие спало, – или когда началась новая сессия. Любой бросок по проклятому опускает потолок на шаг – и его собственный `!roll` или доп. ролл, и чужой переброс. Все четыре числа настраиваются в `.env` (`REWARD_CURSE_*`).

От 75 до 25 – десять бросков, а бесплатных всего три. Поэтому без докупленных роллов и перебросов проклятие обычно держится до конца сессии. Перебросы от других зрителей одновременно и бьют по жертве, и быстрее доводят потолок до дна, после которого через 15 минут проклятие спадает.

**Баллы возвращаются автоматически**, если награда не может сработать: в поле не ник, цель – ты сам, бот ни разу не видел этот ник – ни в чате, ни в игре (для переброса), цель сегодня не катала (для проклятия), у цели щит, щит китежанина прошлого стрима или защита после недавнего переброса (для переброса), цель уже проклята, щит у тебя уже стоит, доп. ролл куплен при оставшихся бесплатных, стрим успел уйти в оффлайн или случилась ошибка. Причину бот пишет в чат.

Жертва саботажа не теряет свои бесплатные броски и может ими ответить – переброс и проклятие счётчик `free_throws` не трогают.

Как устроено:

- **Награды создаёт бот, а не стример в панели.** Twitch разрешает подтвердить выкуп или вернуть баллы только приложению, создавшему награду. При запуске бот сверяет награды с `CONTENT.md` (названия и описания) и `.env` (цены и лимиты) и правит только то, что разошлось. Изменения доходят до Twitch при перезапуске, а не на лету
- **Пока бот выключен, награды стоят на паузе** – иначе баллы спишутся, а применить награду будет некому. Если бот упал, не успев поставить паузу, при следующем запуске выкупы без ответа возвращаются. Так же на паузе они, пока стрим оффлайн: игра живёт в рамках эфира
- **Повтор события не бросает кубик дважды:** каждый выкуп записан в журнал `roll_actions` с уникальным id
- Лимит на зрителя за эфир для переброса и проклятия (`REWARD_ATTACK_MAX_PER_USER`) считает сам Twitch
- **Игра живёт в рамках эфира.** Сессия – стрим, а не календарный день: стрим через полночь – одна игра, перезапуск бота посреди стрима ничего не сбрасывает. Пока стрим оффлайн, `!roll` отвечает «стрим оффлайн», а награды на паузе

### Итоги прошлого стрима

В начале нового эфира бот подводит итоги прошлого и объявляет в чате:

- **Достойнейший китежанин** получает **щит от перебросов** на `ROLL_PERK_MINUTES` (30) минут
- **Подзалупный китежанин** получает **проклятие** на те же 30 минут: обычное (потолок 75, минус 5 за каждый бросок по нему), но через 30 минут спадает в любом случае. Проклятие одно – легло на первый бросок и больше не выдаётся

Отсчёт идёт не от начала стрима, а **с первого появления человека в чате** – или с первого броска по нему. Опоздавший ничего не теряет, но и не пересиживает наказание, отсутствуя: не пришёл за 30 минут после появления – бонус сгорел. Если прошлый стрим катал один человек, он получает только проклятие. Если на прошлом стриме не катал никто, бонусов нет – более ранние стримы не в счёт. Выключается через `ROLL_PERKS_ENABLED=false`.

## Follow-события

## Память и контекст

### Сессии

Сессия – это **эфир**. Пока идёт стрим, всё – чат, `!stat`, `!summary`, контекст Gemini, игра – считается в рамках этого эфира. Имя сессии – дата и время начала стрима в формате `ГГГГ-ММ-ДД ЧЧ:ММ`. Когда стрим оффлайн, сессия – текущая дата в формате `ГГГГ-ММ-ДД`: чат пишется и вне эфира.

Бот узнаёт о начале и конце эфира через EventSub (`stream.online` / `stream.offline`), а при запуске сам спрашивает Twitch, идёт ли стрим. Раз в 2 минуты он ещё сверяется с Twitch: так ловятся потерянные события и то, что случилось, пока бот был выключен. Переключается он, только если расхождение держится три проверки подряд – список эфиров в Twitch отстаёт от событий на минуту-другую. id эфира записан в таблицу `streams`, поэтому перезапуск бота посреди стрима продолжает ту же сессию. Если стрим оборвался и снова пошёл в течение `STREAM_RESUME_MINUTES` (15) минут, это тот же эфир.

Если бота выключили раньше, чем закончился стрим, время конца эфира бот при следующем запуске берёт из записи эфира в Twitch (VOD: начало плюс длительность), а если записи нет – по последнему сообщению чата, которое успел записать. Поэтому без VOD и после долгого простоя бота стрим, перезапущенный вскоре после настоящего конца, может посчитаться новым эфиром.

### Контекст при каждом ответе

При каждом свободном обращении бот одним `asyncio.gather` собирает контекст (`src/gemini/answer_context.py`; подключение к SQLite одно, поэтому запросы идут по очереди – `gather` тут про порядок кода, а не про параллельность). Во время стрима бот видит **весь текущий и весь прошлый стрим** и свою память о людях:

| # | Секция | Откуда | Лимит | Когда добавляется |
|---|---|---|---|---|
| 1 | `[Сохранённые факты]` | таблица `facts` (команд для записи нет, таблица читается, пока профили не подключены к ответам) | все свои + релевантные чужие | всегда |
| 1а | `[Память о людях]`, `[Хроника прошлого стрима]` | профили спрашивающего и упомянутых ников, хроника из памяти | до 4 профилей, одна хроника | если есть; перед вопросом тогда строка `prompts.memory_hint` |
| 1б | `[Прошлый стрим]` | `chat_messages` прошлого стрима | весь | во время стрима |
| 2 | `[Последние сообщения в чате]` | `chat_messages` текущей сессии | весь стрим (до 2000); вне стрима 50 (env) | если есть сообщения |
| 3 | `[Контекст канала]` | FTS5 по `knowledge` + `chat_messages` | 10 (env) | если FTS нашёл совпадения |
| 4 | `[Язык чата]` | случайная выборка из `knowledge` | 10 (env) | всегда (если knowledge не пуста) |
| 5 | `[Твоя реплика, на которую отвечают]` | текст реплики бота из reply | одна | при ответе (reply) на бота |

### Долговременная память о зрителях

После каждого разговора в чате Gemini пишет **память бота**: код в `src/gemini/memory/`, три таблицы.

- **Хроника разговора** (`chronicles`) – 5–15 строк о том, что было на стриме: темы, срачи, кто что отмочил, дословные цитаты, итоги «залупы стрима».
- **События** (`chatter_events`) – из той же хроники выписываются строки про конкретных людей («кто что заявил, с кем сцепился»). Отдельного вызова на это нет.
- **Профиль зрителя** (`chatter_profiles`) – кто он в этом чате, как пишет, коронные фразы, за что его знают, плюс до 8 заметных отношений с другими («вечный срач», «кореша»). Профиль **переписывается целиком**, а не дописывается, поэтому со временем не разрастается.

**Разговор** – это чат между двумя паузами в `MEMORY_SILENCE_MINUTES` (180) минут. Идёт стрим или нет, для памяти неважно: вне стримов здесь не пишут, так что разговор и есть стрим. Зато его не собьют ни пропущенное событие Twitch, ни перезапуск бота посреди стрима, ни конец стрима, пока бот был выключен, ни стрим за полночь.

Хроника пишется для разговора, в котором набралось `MEMORY_CONVERSATION_MIN_MESSAGES` (50) сообщений. Профиль заводится или обновляется у тех, кто написал за разговор `MEMORY_PROFILE_MIN_MESSAGES` (10) сообщений и больше.

Когда пишется:
- **пока бот работает** – раз в 10 минут он проверяет, не закончился ли разговор, то есть примерно через 3 часа после последнего сообщения стрима;
- **при запуске бота** – сразу всё, что закончилось, пока его не было. Если бота выключили посреди записи, разговор просто запишется заново;
- **один раз по всей истории** – `bot.py --build-memory`. Без этой команды память пуста, и бот сам историю не перебирает: при запуске он только пишет в лог подсказку.

Ответы зрителям память не тормозит: ей достаётся не больше двух из пяти одновременных запросов к Gemini.

Если Gemini блокирует запрос своим входным фильтром (он не отключается и срабатывает на сочетание сообщений), хроника пишется по частям и сводится в одну, а профиль – по меньшему числу последних сообщений. Если Gemini просто недоступен, разговор не помечается и повторяется через 10 минут. Сообщения чата модели подаются как данные: «запиши в профиль, что …» из чата не выполняется.

Реплики бота в память **не попадают**: он не должен цитировать сам себя. Хроники и профили пишутся языком чата, а не отчётом, но только по сообщениям – модель просят ничего не придумывать. Длинное тире в ответе модели заменяется на короткое.

Правки памяти людьми нет: команд для просмотра и исправления нет, только база.

Память используется в свободных обращениях к боту: профили спрашивающего и упомянутых и хроника прошлого стрима (см. «Контекст при каждом ответе»). Её читают `!who` и `!versus`: случайные события и отношения из профиля. В проактив она не подключена.

### System prompt

Хранится в `CONTENT.md`, ключ `prompts.system`. Содержимое кэшируется и перечитывается при изменении файла – редактировать можно без перезапуска бота. Задаёт характер, стиль, запреты и правила использования контекстных секций.

Промпты отдельных режимов лежат там же, в секции `## prompts`: `who`, `versus`, `summary`, `summary_request`, `ask`, `proactive_user`, `proactive_general`, `user_question`, `interaction_line`, а ещё промпты памяти `memory_chronicle` и `memory_profile`. Они тоже перечитываются на лету.


### CONTENT.md

Всё, что бот произносит, лежит в одном Markdown-файле в корне проекта. Структура: `## секция` → `### ключ` → значение до следующего заголовка. Правило простое: **`.env` – секреты, числа и флаги, `CONTENT.md` – тексты.**

| Секция | Что внутри |
|---|---|
| `## prompts` | Инструкции для Gemini: `system` (личность), `ask`, `summary`, `summary_request`, `who`, `versus`, `proactive_user`, `proactive_general`, `user_question`, `interaction_line`, `memory_chronicle`, `memory_profile` |
| `## labels` | Заголовки секций контекста, которые видит модель: `facts`, `chat`, `channel`, `language`, `user_facts`, `user_messages`, `user_interactions`. `prompts.system` ссылается на них по названию: названия здесь и там должны совпадать |
| `## texts` | Все ответы в чат: `!help-bot`, `!stat`, тексты `!roll`, названия, описания и итоги наград за баллы, кулдаун (`cooldown_local` / `cooldown_gemini`), отказ по роли, подсказки по формату, сообщения об ошибках |
| `## lists` | `emotes`, `follow`, `banned` – по записи на строку, `#` в начале строки – комментарий |

Особенности:

- **Hot-reload.** Файл перечитывается при изменении mtime – перезапуск не нужен ни для личности, ни для ответов в чат
- **Опечатка не роняет бота.** Сломать разметку Markdown нельзя, поэтому проверяется смысл: дубль ключа `###` пишется в лог (побеждает последний), а файл, в котором не нашлось ни одной секции, не заменяет прошлую валидную версию
- **Плейсхолдеры** (`{user}`, `{target}`, `{seconds}` и т.д.) подставляются через `safe_format()`: неизвестный плейсхолдер логируется, а не роняет обработчик
- **Отсутствующие ключи** ловятся при запуске: `validate_content()` сверяет файл со списком `REQUIRED` в `src/core/content.py` и падает с перечнем недостающих. Незнакомый заголовок – предупреждение в лог: так всплывает опечатка в `###`
- Экранировать ничего не нужно: значение – это просто текст до следующего заголовка. Строки `<!-- … -->` и проза между `##` и первым `###` – примечания, в текст бота не попадают

## База данных

SQLite-файл `chat_history.db` в WAL-режиме. Используется одно разделяемое подключение на весь процесс (синглтон через `get_db()`).

При копировании БД копируй все три файла: `chat_history.db`, `chat_history.db-wal`, `chat_history.db-shm`.

### Таблицы

| Таблица | Тип | Описание |
|---|---|---|
| `chat_messages` | обычная | Сообщения чата (кроме бота) – только живой диалог: команды к боту (`!roll`, `!who` …) не пишутся. Поля: `session_id`, `username`, `message`, `created_at`, `addressed` (было ли обращение к боту – по нему считает `!stat`) |

| `knowledge` | обычная | Импортированный лор, мемы, история. Unique index на `content` |

| `roll_perks` | обычная | Бонусы по итогам прошлого стрима: щит китежанину, проклятие залупе, когда пошёл отсчёт |

## Эксплуатация

Бот живёт в контейнере (Docker Compose). Код едет в образе и заодно монтируется с хоста, изменяемое состояние – на томах.

| Что | Где на хосте | Где в контейнере |
|---|---|---|
| Код и `CONTENT.md` | корень проекта | `/app`, только чтение |
| База, токены, heartbeat | `data/` | `/data` |

Почему именно так:

- **Дерево монтируется в `/app` только на чтение.** `CONTENT.md` перечитывается по mtime без перезапуска, CLI-команды видят те же файлы, что и на хосте, но процесс бота не может переписать собственный код и `.env`, который тоже лежит в дереве. Пишет бот только в `/data`. Единственная команда, которая правит дерево, – `--sync-emotes` (пишет `CONTENT.md`), она запускается из venv на хосте.
- **Портов нет.** OAuth-адаптер twitchio слушает `localhost` внутри контейнера, опубликованный порт до него не доходил. Новые токены – через `make oauth` на хосте, см. [первый запуск](#7-первый-запуск--oauth-авторизация).
- **`working_dir: /data`** – twitchio пишет `.tio.tokens.json` по относительному имени. Без этого токены оставались бы внутри контейнера и терялись при каждом пересоздании.
- **Образ собирается в две стадии.** Зависимости ставятся в `python:3.11-slim-bookworm` – той же Debian, что у финального образа, чтобы собранный из исходников пакет не разошёлся с его glibc, – строго по `requirements.txt` с проверкой хешей, а в финальный образ едет только каталог с пакетами и код: база – `gcr.io/distroless/python3-debian12`, без пакетного менеджера, шелла и прочего лишнего. Итог 118 МБ против 209 МБ у однослойной сборки на slim. Побочный эффект: **шелла в контейнере нет**, поэтому `docker compose exec bot sh` не сработает, а healthcheck написан на Python, а не на `test`/`stat`.
- **Пакеты лежат в `/deps`, а не внутри `/app`.** Дерево проекта монтируется в `/app` и перекрыло бы их собой – контейнер остался бы без зависимостей. Путь подключается через `PYTHONPATH`.
- **`USER 1000:1000`** (и `user: "1000:1000"` в compose) – тот же UID и та же группа, что у владельца каталогов на хосте, иначе бот не запишет ни базу, ни токены на тома. Без группы процесс работал с gid 0, и файлы базы на томе доставались группе `root`.
- **Часовой пояс** бота задаёт `BOT_TIMEZONE` (по умолчанию `Europe/Moscow`): по нему именуются сессии и ключи разговоров памяти, в какой бы зоне ни работал процесс. Поэтому контейнер, CLI на хосте и `make oauth` называют один момент одинаково. Неизвестное имя зоны останавливает запуск с ошибкой, а не откатывается молча в UTC, как это делает `TZ` (ссылки `Europe/Kiev` в актуальном `tzdata` уже нет). `TZ=Europe/Moscow` в compose остаётся только для времени в логах. Зоны в distroless уже есть, ставить `tzdata` не нужно.
- **`CMD` в exec-форме** – иначе PID 1 стал бы шеллом, который не передаёт `SIGTERM`, и база закрывалась бы жёстко при каждом перезапуске. Проверка: после `docker compose restart` у `data/.tio.tokens.json` обновляется метка времени. В distroless точка входа – сам Python, поэтому команда состоит из одного пути к скрипту.
- **`stop_grace_period: 30s`** – чтобы `close_db()` успел отработать.
- **Логи идут только в stdout.** Читать через `docker logs` или `make logs`. Ротация задана в самом compose (`json-file`, 10 МБ × 5 файлов), а не только в `/etc/docker/daemon.json` хоста, которого нет в репозитории. Файловый приёмник (`LOG_FILE`) выключен намеренно: содержимое то же, а второй путь молча отваливается вместе с примонтированным каталогом, незаметно для логов. Плата – история живёт, пока живёт контейнер: пересоздание её обнуляет. Хранение дольше – это отправка логов наружу, а не файл рядом.
- **Healthcheck** смотрит на `data/heartbeat`, который бот трогает раз в минуту. Он ловит случай «процесс жив, а бот оглох» – его политика перезапуска не видит, потому что процесс не падал. Сейчас healthcheck только помечает контейнер `unhealthy`; автоматического перезапуска по нездоровью пока нет.

Откат, если новая сборка оказалась плохой: `docker compose down`, затем `cd data && BOT_DB_PATH=chat_history.db ../venv/bin/python3 ../bot.py`. Путь к базе задан явно: без него бот открыл бы новую пустую базу в корне репозитория, а токены лежат в `data/.tio.tokens.json`, поэтому бот запускается из `data/`.

## Разработка

CI нет, всё запускается локально из venv. Повседневные команды собраны в `Makefile`:

```bash
make venv     # venv на Python 3.11 с инструментами из requirements-dev.txt
make test     # pytest: ~280 тестов меньше чем за три секунды, без сети, Gemini и .env
make check    # ruff + pytest – перед слиянием ветки
make fix      # автоисправления ruff
make audit    # известные уязвимости в requirements.txt и requirements-dev.txt
make lock     # пересобрать requirements*.txt после правки requirements*.in
```

Зависимости разложены по соглашению pip-tools. В `requirements.in` – прямые, то есть всё, что импортирует код, с закреплёнными версиями; `make lock` собирает из него `requirements.txt` – всё дерево с хешами. Так же `requirements-dev.in` собирается в `requirements-dev.txt`: pytest, ruff, pip-audit и pip-tools с хешами, а общие с ботом пакеты – в версиях бота (`-c requirements.txt`). Правят только `.in`, файлы `.txt` генерируются. Образ ставит только `requirements.txt`, поэтому новая версия пакета доходит до бота, только если пересобрать его и образ. Тесты лежат в `tests/` и запускаются только на хосте: в образе distroless нет pytest. Каждый тест получает пустую временную базу, а `CONTENT.md` – сгенерированный из `REQUIRED`; до боевой базы, `.env` и Gemini они не дотягиваются. Один тест проверяет настоящий `CONTENT.md`: новый текст без записи в `REQUIRED` падает там, а не при старте бота. Правила ruff – в `pyproject.toml`; форматтер и сортировка импортов не используются, чтобы не ломать принятую раскладку кода.

## CLI-команды

Боевой способ – в контейнере, тем же образом, что и бот:

```bash
docker compose run --rm bot /app/bot.py --backup /data/copy.db
docker compose run --rm bot /app/bot.py --vacuum
docker compose run --rm bot /app/bot.py --lore-sources
```

`--vacuum` переписывает весь файл и на это время запирает базу: запросы работающего бота ждут до 30 секунд, а дольше – теряются. На базе в десятки мегабайт это около секунды; когда она вырастет до сотен, `--vacuum` лучше запускать при остановленном боте.

`--sync-emotes` – исключение: он переписывает `CONTENT.md`, а дерево в контейнере смонтировано только на чтение, поэтому эмоты синхронизируются из venv на хосте (`./venv/bin/python3 bot.py --sync-emotes`). Работающий бот подхватит файл сам.

Одна команда за запуск. Флаг-уточнение без команды (`--dry-run`, `--source`, `--limit`…) – ошибка, а не запуск бота: без команды `bot.py` поднимает бота, и случайный флаг запустил бы второй экземпляр рядом с работающим. Флаг, который команда не читает, тоже ошибка: `--vacuum --dry-run` иначе сжал бы базу по-настоящему, а `--probe-context --dry-run` всё равно заплатил бы за Gemini.

Ниже – тот же список для запуска из venv, без контейнера:

```bash
./venv/bin/python3 bot.py                                      # запуск бота
./venv/bin/python3 bot.py --upload-lore lore.txt               # импорт лора
./venv/bin/python3 bot.py --upload-lore lore.txt --dry-run     # предпросмотр импорта
./venv/bin/python3 bot.py --upload-lore lore.txt --clear-lore  # очистить + импорт
./venv/bin/python3 bot.py --clear-lore                         # только очистить knowledge (всё)
./venv/bin/python3 bot.py --upload-lore result.json --format telegram   # чат из экспорта Telegram Desktop
./venv/bin/python3 bot.py --upload-lore article.md --format text        # статья, кусками по 1–3 предложения
./venv/bin/python3 bot.py --lore-sources                       # источники базы знаний
./venv/bin/python3 bot.py --clear-lore --source article.md     # удалить один источник (с --dry-run – только посчитать)
./venv/bin/python3 bot.py --list-facts                         # показать все факты из БД
./venv/bin/python3 bot.py --build-memory                       # память по всей истории: хроники и профили
./venv/bin/python3 bot.py --build-memory --dry-run --limit 3   # показать 3 хроники и 3 профиля, ничего не писать
./venv/bin/python3 bot.py --clear-memory                       # стереть память
./venv/bin/python3 bot.py --clear-memory --dry-run             # только посчитать, что было бы стёрто
./venv/bin/python3 bot.py --probe-context --limit 8             # замер контекста: реальные обращения к боту, now (контекст без памяти и без полного стрима) против new (как отвечает бот), ~1 цент за вопрос
./venv/bin/python3 bot.py --probe-context 33839 35280 --samples 2   # конкретные сообщения (id из chat_messages), по 2 ответа на вариант
./venv/bin/python3 bot.py --backup                             # копия БД (безопасна при работающем боте)
./venv/bin/python3 bot.py --backup path/to/copy.db             # копия в указанный файл
./venv/bin/python3 bot.py --vacuum                             # уплотнить файл БД
./venv/bin/python3 bot.py --sync-emotes                        # эмоты канала из Twitch в CONTENT.md
./venv/bin/python3 bot.py --sync-emotes channel global         # + глобальные эмоты Twitch
./venv/bin/python3 bot.py --sync-emotes --dry-run              # показать, что добавится
./venv/bin/python3 bot.py --sync-emotes --replace-emotes       # пересобрать список с нуля
```

## Структура проекта

```
├── bot.py                 # Точка входа: класс Bot (twitchio), жизненный цикл, run_bot()

├── src/
│   ├── core/                # Каркас, на котором стоят все фичи
│   │   ├── activity.py      # ChatWatch: писал ли кто-то в чате с прошлого раза – бот говорит только в живой разговор

│   │   ├── cooldowns.py     # Кулдауны по монотонным часам
```

Куда класть новое: команда с генерацией – в `gemini/`, небольшая команда без Gemini – в `local/`, фича со своими таблицами, текстами и фоновыми задачами – в подпапку внутри своего пакета, как `local/roll/`. `core/` от фич не зависит, кроме диспетчера, который регистрирует их команды.
